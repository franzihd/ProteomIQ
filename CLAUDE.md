# ProteomIQ

A protein-level joint embedding space for proteomics and natural language, trained contrastively on CPTAC, that allows a researcher to query the biological meaning of proteins in their own patient sample using natural language.

## Project goal

Build a CLIP-style model at **protein granularity**:
- Each training pair is one `(protein, patient)` combination — the protein's amino acid sequence embedding (from ESM2) combined with its measured abundance value in that patient
- The matching text description combines the protein's UniProt functional annotation with the clinical context of that patient
- At inference: a researcher provides a text query (e.g. "proteins associated with lung cancer") and a new patient sample; nearest-neighbor search over that sample's ~8,000 protein embeddings returns the most biologically relevant proteins

**Why protein-level (not patient-level):** querying at the patient level returns other patients — not useful. Querying at the protein level returns specific proteins like EGFR, MET, KRAS — directly actionable biological insight.

The closest prior work is [CellWhisperer](https://github.com/theislab/CellWhisperer), which does the same for single-cell transcriptomics (scRNA-seq). ProteomIQ targets mass-spectrometry-based proteomics instead.

## Architecture

### Training
```
protein sequence → ESM2 (frozen, pre-computed) ─┐
                                                  ├─→ MLP projection → embedding
abundance scalar (from CPTAC) ────────────────────┘

UniProt description + patient clinical text → BioBERT → MLP projection → embedding
```
Contrastive loss (NT-Xent / InfoNCE) pulls matching `(protein_in_patient, text)` pairs together and pushes non-matching pairs apart.

Scale: ~1,100 patients × ~12,000 proteins ≈ **13 million training pairs** across all CPTAC cohorts. Initial development uses LUAD only (~1.7M pairs).

### Inference
```
researcher query text → BioBERT → embedding
                                       ↓
                    nearest-neighbor search over ~8,000 protein vectors
                    (pre-encoded from the new patient sample)
                                       ↓
                    ranked list: EGFR (0.94), MET (0.91), KRAS (0.87) …
```

### Key design decisions
- **ESM2 is frozen** — run once on all protein sequences offline, embeddings saved to disk. Only the MLP projection heads are trained. This makes training feasible without fine-tuning a large model.
- **ESM2 model choice**: `esm2_t30_150M` (150M params) is the recommended balance of quality vs. compute. `esm2_t6_8M` is faster for prototyping.
- **Abundance as scalar**: concatenated to the ESM2 embedding before the MLP. Encodes expression level as a biological signal. Raw abundance values are **rank-normalized to percentiles (0–1) within each patient sample** before use — this makes values scale-invariant and comparable across experiments, which is essential because a researcher's uploaded abundance matrix at inference time will come from a different instrument and normalization than the CPTAC training data. Absolute values are meaningless across experiments; relative rank within a sample is not.
  - **Known limitation:** within-sample rank conflates a protein's *natural baseline abundance* with its *actual regulation*. A naturally abundant protein (e.g. albumin) will always rank near 1.0 regardless of whether it is truly overexpressed. The scalar therefore captures "relative abundance among all measured proteins in this sample," not "upregulation relative to this protein's own baseline." Correcting for this would require cross-patient reference statistics that are not available at inference time when a researcher uploads a single new sample. This is an accepted trade-off; the ESM2 embedding already encodes protein identity, so the model can learn that some proteins are consistently high-ranked.
- **Text = UniProt + clinical**: UniProt annotation is static per protein (reused across all patients); clinical description is static per patient (generated by `text_generation.py`). Concatenated to form the per-`(protein, patient)` text.

## Domain glossary

- **Proteomics**: large-scale study of all proteins expressed in a cell, tissue, or organism — measured with mass spectrometry
- **CPTAC**: Clinical Proteomic Tumor Analysis Consortium — the main data source (`cptac` Python package)
- **LUAD**: Lung Adenocarcinoma — the cancer type currently used as the first dataset
- **Protein abundance matrix**: rows = samples (patients), columns = proteins (identified by gene name + database ID, stored as a two-level MultiIndex), values = measured expression levels
- **NaN**: Not a Number — missing value, common in proteomics when a protein was not detected in a sample
- **CLIP**: Contrastive Language-Image Pretraining — trains two encoders (one per modality) with a contrastive loss so matching pairs end up close in a shared embedding space
- **Contrastive loss**: loss function that pulls embeddings of matching pairs together and pushes non-matching pairs apart; NT-Xent and InfoNCE are common variants
- **Nearest-neighbor search**: given a query embedding, find the k most similar embeddings by cosine or Euclidean distance (e.g. via FAISS or `sklearn`)
- **ESM2**: protein language model by Meta, pre-trained on millions of protein sequences; produces rich per-protein embeddings that capture structure and function. Used here as a frozen feature extractor.
- **UniProt**: protein database containing curated functional annotations for human proteins (gene function, biological process, disease associations); the source of protein-side text descriptions
- **NT-Xent / InfoNCE**: the standard contrastive loss used in CLIP — for each sample in a batch, the matching pair is the positive and all other pairs are negatives

## UniProt fetching

`src/Textual/fetch_uniprot.py` fetches protein annotations and sequences for a cohort's proteins via the UniProt REST API.

**How it works:**
1. Extracts ENSP IDs from the second header row of `proteomics_raw.csv`
2. Submits a batch ID mapping job to the UniProt REST API (`Ensembl_Protein` → `UniProtKB`)
3. Polls the status endpoint until the job is done (checks for `jobStatus` key in response — if present, job is still running, wait 5 seconds and retry)
4. Paginates through all result pages (25 per page) following `Link` headers
5. Saves to `data/{cohort}/protein_annotations.csv`

**Output columns:** `ENSP_ID`, `UniProt_Accession`, `Gene`, `Annotation`, `Sequence`

**API note:** UniProt caches job submissions — same input always returns the same `jobId`. The stream endpoint (`/idmapping/stream/`) can expire; use the status endpoint with pagination instead.

**Annotation format:** gene name is prepended to the annotation text, e.g. `"ARF5: GTP-binding protein involved in protein trafficking..."` so BioBERT always sees the protein name.

**Protein overlap across cohorts:** many proteins appear in multiple cohorts (EGFR, KRAS etc. are present in all cancers) and will have identical UniProt annotations. The per-cohort approach accepts this redundancy for simplicity. A future optimization would maintain one unified `protein_annotations.csv` covering the union of all cohorts.

**To run:**

## Text generation

The text side of each training pair is: **UniProt protein description** + **patient clinical description**, concatenated at training time (not saved to disk — would be ~1.27M rows).

**Do not save combined texts to disk.** Generate `(protein, patient)` pairs on-the-fly during training by joining `protein_annotations.csv` and `descriptions.csv`. Only save the resulting BioBERT embeddings (1.27M × 768 floats ≈ ~4GB).

`src/text_generation.py` handles the patient clinical description half. It converts a clinical metadata row into a natural-language sentence for BioBERT embedding. Each description is a flexible comma-separated sentence — only fields with valid values are included, so length varies per patient.

The UniProt description half (one per protein, reused across patients) is not yet implemented.

**Public API:**
- `is_usable(value)` — returns `False` for NaN, any value in `SKIP_VALUES`, or strings starting with `"Other:"`; `True` otherwise
- `clinical_to_text(row, cancer_type)` — builds a description string from one patient row; `cancer_type` is passed as a parameter (e.g. `"lung adenocarcinoma"`)
- `generate_descriptions(clinical_df, cancer_type)` — applies `clinical_to_text` to every row; returns `{patient_id: description}` dict
- `save_descriptions(descriptions, output_path)` — writes the dict as a CSV with patient ID as index and a `"description"` column

**Columns used** (in order):
- `age`, `sex` — patient demographics; `age` is parsed via `int(float(age))` to handle values like `">=90"` which fall back to raw string
- `ethnicity_race_ancestry_identified` — ancestry
- `tumor_stage_pathological` — Stage I/II/III/IV
- `histologic_type` — cancer subtype
- `histologic_grade` — G1/G2/G3
- `number_of_lymph_nodes_positive_for_tumor_by_he_staining` — lymph node status: 0 → "lymph node negative", N → "N lymph nodes positive"; parsed via `int(float(...))` wrapped in try/except for non-numeric values
- `tumor_necrosis` — "Present" → "tumor necrosis present"; "Not identified" is skipped
- `margin_status` — "uninvolved" → "clear surgical margins"; "involved" → "positive surgical margins"
- `tumor_size_cm` — tumor size in cm
- `tumor_laterality` — left or right (lung/kidney)
- `tumor_site` — upper/lower/middle lobe (lung only)
- `tumor_focality` — unifocal or multifocal
- `tobacco_smoking_history` — mapped to: "lifelong non-smoker", "current smoker", "former smoker (>15 years)", "former smoker (<15 years)"
- `alcohol_consumption` — mapped to: "lifelong non-drinker", "moderate drinker", "heavy drinker", "former drinker"
- `bmi` — categorized as "underweight" (<18.5), "normal weight" (<25), "overweight" (<30), "obese" (≥30), shown with raw value

**Key design decisions:**
- Values in `SKIP_VALUES` (a long list covering "Unknown", "Not Reported", "not specified", etc.) are silently omitted
- Cohort-specific columns (e.g. lymph nodes, tumor necrosis, margin status) are safe to include for all cohorts — `row.get()` returns `None` for missing columns and `is_usable(None)` returns `False`, so they are silently skipped
- Raw verbose smoking/alcohol strings are mapped to short phrases via lookup dicts (`SMOKING_DICT`, `ALCOHOL_MAP`); unrecognized values fall through as-is
- `cancer_type` is passed as a parameter, not read from the CSV — mapped from cohort name via `CANCER_TYPES` dict in `__main__`
- BioBERT handles variable-length sentences — no fixed template needed


## Abundance rank normalization

`src/preprocessing/rank_normalize.py` rank-normalizes the raw proteomics abundance matrix and saves the result to `data/luad/rank_normalized_proteomics.csv`.

**What it does:** for each patient (row), it replaces every protein's raw abundance value with its percentile rank among all proteins measured in that patient. Values become [0, 1]; NaN stays NaN.

**Why within-sample:** a researcher uploads one new sample at inference time with no other samples to compare against. Within-sample rank is instrument-agnostic — a protein at the 90th percentile in a CPTAC experiment and the 90th percentile in a new hospital's mass spec mean the same thing: highly expressed relative to everything else in this patient.

**Known limitation:** within-sample rank conflates natural baseline abundance with actual regulation. A naturally abundant protein (albumin) will always score near 1.0 even when not dysregulated. The scalar captures "relative abundance in this sample," not "upregulation vs. this protein's own baseline." This is an accepted trade-off since true per-protein baseline normalization requires cross-sample reference data unavailable at inference.

**To run:**
```bash
uv run python src/preprocessing/rank_normalize.py --cohort luad
```

**Output (LUAD):** 213 × 13,302, values in [0, 1], NaN count unchanged (534,935).
**Output (GBM):** 110 × 13,002, values in [0, 1], NaN count unchanged (237,778) — 16.6% missing, comparable to LUAD.

## ESM2 embedding

`src/embeddings/protein/esm2_embeddings.py` pre-computes ESM2 sequence embeddings for all LUAD proteins and saves them to `data/luad/esm2_embeddings.h5`.

**What it computes:** for every protein in `protein_annotations.csv` (with both `Sequence` and `Annotation`), it runs the amino acid sequence through ESM2 and mean-pools the token representations into a single 640-dim vector.

**Model:** `esm2_t30_150M_UR50D` — 30 layers, 150M parameters, 640-dim embeddings. Weights downloaded automatically on first run to `~/.cache/torch/hub/checkpoints/`.

**Output file structure (`esm2_embeddings.h5`):**
- `embeddings` — shape `(11485, 640)`, float32 — one 640-dim vector per protein
- `protein_ids` — array of 11485 ENSP ID strings (row index)
- `completed` — boolean array of length 11485. `completed[i] = True` means batch containing protein `i` is fully written

**Resume logic:** same pattern as BioBERT script. On restart, skips any batch already marked `True` in `completed`. Stopping mid-run loses at most one batch (32 proteins).

**Sequence truncation:** sequences longer than 1022 amino acids are truncated — ESM2's positional embeddings are only defined up to 1022 tokens.

**To restart from scratch:** `rm data/{cohort}/esm2_embeddings.h5` then rerun.

**Runtime:** ~13 minutes on RTX A6000 per cohort (~11,000–13,000 proteins).

**To run:**
```bash
uv run python src/embeddings/protein/esm2_embeddings.py --cohort lscc
```

## BioBERT embedding

`src/embeddings/textual/embed_biobert.py` pre-computes all BioBERT text embeddings for LUAD and saves them to `data/luad/biobert_embeddings.h5`.

**What it computes:** for every `(protein, patient)` pair, it concatenates the protein's UniProt annotation + the patient's clinical description into one string and runs it through BioBERT. Result: one 768-dim embedding per pair.

**Output file structure (`biobert_embeddings.h5`):**
- `embeddings` — shape `(111, 11485, 768)`, float32 — the main cube. `embeddings[p, q, :]` = embedding for patient `p`, protein `q`
- `patient_ids` — array of 111 patient ID strings (row index)
- `protein_ids` — array of 11485 ENSP ID strings (column index)
- `completed` — boolean array of length 111. `completed[p] = True` means patient `p` is fully written to disk

**Resume logic:** the script supports stop/resume. On first run it creates the file (`"w"` mode). On restart it opens the existing file (`"r+"` mode), reads `completed`, and skips any patient already marked `True`. After writing each patient's embeddings, it immediately sets `completed[p_idx] = True` on disk — so stopping mid-run loses at most one patient's work.

**To restart from scratch:** `rm data/{cohort}/biobert_embeddings.h5` then rerun.

**Runtime:** ~60 minutes on RTX A6000 per ~110 patients. Full multi-cohort (~1,100 patients) ≈ 9–10 hours total.

**To run:**

## Dataset

`src/model/dataset.py` implements `ProteomicsDataset` — a PyTorch `Dataset` that assembles training pairs from the three pre-computed data sources.

**What it does:** on construction, it loads all three sources into memory, computes the intersection of proteins and patients present in all sources, iterates over every valid `(patient, protein)` combination, and stores only those pairs where the abundance value is not NaN. `__getitem__` concatenates the ESM2 vector with the abundance scalar to produce the 641-dim protein embedding and looks up the pre-computed BioBERT embedding for the same pair.

**Inputs:**
- `data/luad/rank_normalized_proteomics.csv` — 213 patients × 13,302 proteins, values in [0, 1]
- `data/luad/esm2_embeddings.h5` — 11,485 proteins × 640-dim
- `data/luad/biobert_embeddings.h5` — 111 patients × 11,485 proteins × 768-dim

**Alignment logic:** the abundance matrix has 213 patients; BioBERT only covers 111 (those with clinical descriptions). The dataset intersects both sets so only patients with all three data sources are used.

**Output per `__getitem__`:**
- `protein_emb` — shape `(641,)`: ESM2 640-dim + abundance scalar
- `text_emb` — shape `(768,)`: BioBERT embedding for the same `(patient, protein)` pair

**Expected dataset size:** ~111 patients × ~11,000 proteins × ~85% non-NaN ≈ ~1.0M training pairs (confirmed: 1,052,388).

## Training

`src/model/train.py` trains the two projection heads with InfoNCE (NT-Xent) contrastive loss.

**What is trained:** only the two MLP projection heads (protein: 641→512→256, text: 768→512→256). Both ESM2 and BioBERT are permanently frozen — their embeddings are pre-computed on disk and never updated.

**Hyperparameters (following CellWhisperer):**
- Batch size: 512
- Epochs: 16
- Max learning rate: 1e-5
- LR schedule: linear warmup for first 3% of steps (`get_cosine_schedule_with_warmup` from `transformers`) → cosine decay for remaining 97%
- Temperature: fixed at 0.07 (logits scaled by `1/0.07` before the loss, as in the original CLIP paper)

**Loss:** for a batch of N pairs, the L2-normalized protein and text vectors are matmul'd into an N×N cosine-similarity matrix. The diagonal holds the matching pairs; cross-entropy (with `labels = arange(N)`) is computed in both directions — protein→text (`logits`) and text→protein (`logits.T`) — and averaged for a symmetric loss.

**Patient-level test split:** 10 of the 111 LUAD patients are randomly held out (`random.seed(42)`, so the split is reproducible) *before* the dataloader is built — `dataset.pairs` is overwritten to contain only the training patients' pairs. Splitting is done at the **patient** level (not pair level) to avoid leakage: a held-out patient's proteins must never appear in training. The held-out patient IDs are saved to `data/luad/test_patients.json`.

**Checkpointing:** at the end of every epoch, both projection heads' `state_dict()`s are saved (overwriting) to `data/luad/checkpoint.pt` as `{"protein_head": ..., "text_head": ...}`.

**Difference from CellWhisperer:** CellWhisperer unfreezes BioBERT partway through training, allowing the text encoder to adapt to the biological domain. ProteomIQ keeps BioBERT frozen throughout because (a) outputs are pre-cached and (b) 111 unique patients is too small to fine-tune BioBERT without overfitting. This is an accepted limitation — future work could fine-tune BioBERT on the full multi-cohort dataset.

**To run:**
```bash
uv run python src/model/train.py
```

**Confirmed result (LUAD, 16 epochs, batch 512, 10 patients held out):** loss converged from 4.79 → 0.86 — a healthy curve (random baseline for batch 512 is `log(512) ≈ 6.24`). Runtime: a few minutes on the RTX A6000, since only the small projection heads are trained (ESM2/BioBERT stay frozen).

**Note on paths:** `checkpoint.pt` and `test_patients.json` are currently saved under `data/luad/` — hardcoded for the LUAD-only proof of concept. When scaling to multi-cohort training, parametrize these paths by run/cohort name so different runs don't overwrite each other.

## Inference and evaluation

`src/model/evaluate.py` runs the sanity-check query pipeline on a held-out test patient using the trained checkpoint.

At inference/evaluation:
1. Load the trained checkpoint (`data/luad/checkpoint.pt`) into fresh `ProjectionHead` instances, set to `.eval()`
2. Pick a held-out test patient (from `data/luad/test_patients.json`)
3. For each of that patient's measured proteins (non-NaN abundance, present in ESM2): concatenate ESM2 embedding + abundance scalar → protein projection head → 256-dim vector. **ESM2 is reused via lookup, not rerun** — a protein's amino-acid sequence (and therefore its ESM2 embedding) is identical across patients; only a brand-new, never-before-seen protein sequence would require running ESM2 live.
4. Encode the query text (e.g. "kinase activity") live with BioBERT (mean-pooled, using `mean_pool`/`MAX_LENGTH` from `embed_biobert.py`) → text projection head → 256-dim vector. Unlike the protein side, the query text is new and must be encoded on the spot — it was never pre-cached, since `biobert_embeddings.h5` only contains `(protein annotation + clinical description)` pairs from training.
5. Cosine similarity (dot product of L2-normalized vectors) between the query vector and all of the patient's protein vectors → sort descending → ranked list

**To run:**


## Planned tool: Streamlit interface with LLM interpretation

The long-term vision for ProteomIQ is a researcher-facing tool where a user uploads their own proteomics data and has a natural language conversation about it — similar in spirit to CellWhisperer, but for mass-spectrometry proteomics.

### What the tool does

```
Researcher uploads: abundance_matrix.csv

Researcher: "What's going on with this patient?"

Tool: "This patient shows strong activation of growth factor signaling —
EGFR, MET and SRC are among the highest-ranked proteins. Combined with
elevated cell cycle proteins like CDK1 and CCNB1, this suggests a highly
proliferative tumor. Immune signaling appears relatively low, which may
indicate immune evasion."

Researcher: "Could this patient be resistant to EGFR inhibitors?"

Tool: "Possibly — MET and AXL both rank in the top 50, which are known
bypass resistance mechanisms when EGFR is inhibited."
```

### How it works (pipeline)

```
1. Researcher uploads CSV (proteins × abundance values)
2. Rank-normalize abundances within the sample [0, 1]
3. Look up pre-computed ESM2 embeddings for each protein
4. Concatenate ESM2 + abundance → protein projection head → 256-dim vectors
5. Researcher asks a question in plain language
6. BioBERT + text projection head encodes the question → 256-dim query vector
7. Cosine similarity → top-20 most relevant proteins retrieved
8. Top proteins + abundances + question sent to Claude API
9. Claude returns a natural language biological interpretation
```

### Key design note: retrieval vs. interpretation

The ProteomIQ model does **retrieval** — it finds which proteins are semantically relevant to a query. The LLM (Claude) does **interpretation** — it explains what those proteins mean biologically and clinically. Neither component alone is sufficient; together they produce a useful tool.

### Why abundance weighting is essential for patient-specificity

Pure semantic retrieval (cosine similarity alone) is essentially a **protein function lookup** — the same proteins rank highly for "RTK signaling" in every patient, because the ranking is dominated by the ESM2 embedding (protein sequence/function, identical across patients). This is no more useful than searching UniProt directly.

The tool only becomes patient-specific when **abundance is factored in**. Multiplying cosine similarity by abundance rank gives a combined score that reflects both semantic relevance and actual expression in this patient:

```
activity_score = cosine_similarity × abundance_rank
```

A protein at 0.8 semantic similarity but 5th percentile abundance is probably not driving anything in this patient. A protein at 0.6 similarity but 95th percentile abundance likely is. This weighting is what makes ProteomIQ answer a question GSEA cannot: **"which proteins are BOTH functionally related to concept X AND highly expressed in THIS specific patient?"** — using free-text natural language rather than fixed pathway gene sets.

`activity_score` should be the default ranking in the Streamlit app, not raw cosine similarity.

### What questions the tool can answer

- "Which proteins are most relevant to [any biological concept]?"
- "What does this patient's overall proteomic profile suggest?"
- "Could this patient be resistant to [drug]?"
- "What's the most striking finding in this sample?"
- "Which proteins here are associated with poor prognosis?"

### Tech stack for the tool

- **Streamlit** — UI (file upload + chat interface, Python-native, fast to build)
- **ProteomIQ retrieval model** — finds relevant proteins for any text query
- **Claude API** — interprets retrieved proteins in natural language
- Pre-computed ESM2 embeddings loaded at startup for fast inference

### Known limitations of the tool

- The model cannot say a protein is "overexpressed" — within-sample rank only captures relative abundance, not dysregulation vs. a baseline
- Abundance scalar contribution is uncertain — the model likely learned primarily from protein identity (sequence), not from abundance variation across patients. An ablation (train without abundance scalar, compare R@K) would quantify this.
- The LLM interpretation depends on what the retrieval model returns — if retrieval is wrong, the LLM explanation will also be wrong
- Not a replacement for established bioinformatics tools (GSEA, Enrichr) — best used for hypothesis generation and exploratory analysis
- **R@K limitation — name shortcut:** both ESM2 and BioBERT encode protein identity (ESM2 via unique sequence, BioBERT via gene name in UniProt annotation e.g. "EGFR: receptor tyrosine kinase..."). The model may be learning name matching rather than purely biological function. A stricter evaluation would mask the gene name from the annotation text. This is worth one sentence of acknowledgment in the thesis as a known limitation.

## Next steps (as of 2026-07-07) — retraining plan and architecture decisions

### Decision: drop clinical description from training text, keep abundance in the protein input
Following 8e's result, the next retrain changes the **text side only**: train against **UniProt annotation only** (no clinical description), GO terms to be added in a follow-up retrain. Rationale, in order:

1. **Fixes a real train/inference mismatch, independently discovered while reasoning through this.** Training text was always `UniProt annotation + patient clinical description`, but the query at inference (`evaluate.py`, and the planned Streamlit tool) is always just a plain researcher question — clinical description was never part of any real query. Training text and inference text were in different formats the whole time.
2. **Matches CellWhisperer's actual design discipline**, on inspection (see below): numbers belong in the numeric encoder (abundance, already true), text should describe pure identity/function, and clinical/sample context belongs in a separate, downstream step — not fused into the retrieval training pairs.
3. **One variable per experiment.** Abundance stays in the 641-dim protein input, unchanged, specifically so this retrain isolates exactly one change (text side). The already-planned abundance ablation (train with vs. without the scalar) is a *separate* experiment, to be run against this new baseline, not bundled into it.
4. GO-term augmentation is deferred to a second retrain on top of this one (also a one-variable-at-a-time decision), rather than combined in a single step — costs one extra retrain cycle, but keeps attribution clean. Given the 2-month window this could be revisited to combine both into one retrain if time pressure demands it; if so, note explicitly that the result would be confounded between the two changes.

**Practical effect:** since text no longer varies per patient, `biobert_embeddings.h5` collapses from `(patients × proteins × 768)` to `(proteins × 768)` — one embedding per protein instead of per `(patient, protein)` pair. This is a large compute/storage win (the ~9-10 hour multi-cohort BioBERT runtime should drop to roughly the same order as the ESM2 pass, since it's now also one forward pass per protein). The *number of training pairs* for the InfoNCE loss is unaffected (still ~1M-13M) — pair count is set by how many `(patient, protein)` combinations have a measured, non-NaN abundance value (a data-availability fact, gated in `dataset.py`), not by whether text varies per patient.

### Theoretical finding: this likely removes any training incentive for abundance to matter
Worked through carefully before committing to the retrain: with `clinical_description` removed, the text target for a given protein is identical across every patient. In a typical training batch (512 pairs sampled from millions), a same-protein-from-two-different-patients collision is rare — nearly every negative in a batch is a genuinely different protein, already trivially distinguishable via the 640-dim ESM2 embedding alone. So InfoNCE can reach near-zero loss by learning "map each protein's ESM2 fingerprint to its own fixed UniProt-text point" while **completely ignoring the abundance dimension** — ignoring it costs nothing, since two patients' copies of the same protein still both correctly match the identical text target regardless. The original design's only real incentive for abundance to matter was that clinical description made the *text* side patient-specific too, giving the model a reason to make the *protein* side patient-specific in response. Removing it removes that incentive. This is consistent with, and reinforces, the existing "Abundance scalar contribution is uncertain" limitation noted above (line ~513) — under the *original* design (with clinical description) that contribution was already suspected to be small; under the *new* design it plausibly drops further, for a specific, identifiable reason rather than just suspicion.

**Why this isn't fatal:** patient-specific ranking doesn't have to come from the learned embedding. `activity_score = cosine_similarity(query, protein_embedding) × abundance_rank` (already planned, see line ~763) computes patient-specificity **at inference, from the raw abundance value directly** — it does not require abundance to have been meaningfully absorbed into the trained representation at all. `cosine_similarity` handles "how relevant is this protein to the query, generically" (Stage 1's job); multiplying by the patient's own raw `abundance_rank` handles "and is it actually expressed in this specific patient" (a data lookup, not a learned quantity). This resolves the standing worry about patient-specificity cleanly: implement and test `activity_score` on real query/patient examples as a near-term, low-cost step, independent of whatever the retrain's embedding does or doesn't learn about abundance.

### CellWhisperer comparison, clarified (relevant for Related Work / justifying design choices)
Checked directly against CellWhisperer's public methodology (paper abstract, GitHub README — full paper is paywalled) before assuming parity:
- **Granularity differs fundamentally.** CellWhisperer pairs one whole transcriptome (one cell/sample) with one caption describing that sample's identity (cell type, tissue, disease). It never splits "molecule identity" from "sample context" the way ProteomIQ does, because it operates at cell/sample granularity, not gene granularity — there is no CellWhisperer equivalent of "UniProt annotation + clinical description," because it never needed one. ProteomIQ's protein-level choice (deliberate, and the actual thesis differentiator — see "Why protein-level" in Project goal) is what created this two-level text-fusion problem in the first place; CellWhisperer offers no ready-made precedent to copy for it.
- **CellWhisperer's chat interface is a fine-tuned LLaVA-style model, not a prompted API call.** It uses a trainable adapter to inject raw transcriptome-embedding vectors directly into an LLM's context, then fine-tunes (adapter, often the LLM itself too) on curated `(embedding, question, answer)` data — a substantial additional research effort (open-weight LLM access, custom instruction-tuning dataset, extra compute).
- **Decision: do not pursue LLM fine-tuning.** ProteomIQ's planned LLM-interpretation step (Claude API, given retrieved proteins + abundances + UniProt text + clinical description as a plain-text prompt, see "Planned tool" section) achieves the same end-user goal (natural-language interpretation of retrieval results) without any fine-tuning, using Claude's existing pretrained knowledge via in-context prompting. This is also the only option available in practice — Anthropic does not offer end-users raw-embedding injection or fine-tuning of Claude's internals the way LLaVA-style approaches require open-weight models. No further evaluation of this alternative is planned given the 2-month timeline.

### Stretch goal (optional, sequenced after the core retraining plan): hierarchical sample-level embedding
An idea for restoring a *learned* (not just post-hoc) patient-specific signal, worth recording even though not immediately actioned: pool all of a patient's protein-in-sample embeddings `h[j,i]` via **abundance-weighted pooling** (`z_sample[j] = sum_i normalize(abundance[j,i]) * h[j,i]`) into one whole-sample embedding, project it, and align it against the patient's clinical description with a second, separate contrastive loss — architecturally this is CellWhisperer's actual cell-level mechanism, added *alongside* (not replacing) protein-level embeddings. The abundance-weighted pooling step is the key insight: it guarantees the sample embedding varies by each patient's abundance *pattern* even if `protein_mlp` itself never learns to use the abundance dimension internally, since the pooling weights come directly from raw abundance regardless. Assessed as sound but out of scope for now: bringing clinical description back in here is fine (no mismatch — the anticipated sample-level query register matches a clinical-description-style target, unlike the protein-level case), but it requires a materially bigger engineering lift (new pooling mechanism, new projection head, a second loss to balance, and a restructured per-patient batching scheme, vs. the current per-`(patient,protein)`-pair batching). If pursued, do it **staged**: freeze the Stage 1 `protein_head` from the core retrain, and train only the new pooling + sample-projection + clinical-text head on top of it, rather than building one large joint system from scratch. Only worth attempting if the core retraining plan (drop clinical description → GO terms → `activity_score` validation) is done with time remaining.

(UniProt annotation + clinical description) → BioBERT (frozen) → 768-dim vector per (protein, patient) pair.
Saved to `data/{cohort}/biobert_embeddings.h5`. Runtime ~60 min per ~110 patients.

Why pre-compute: ESM2 and BioBERT are large models — computing embeddings once and caching them makes training feasible without fine-tuning.

### 5. Model architecture
`src/model/projection_head.py` — shared MLP architecture (LayerNorm + ReLU + L2 norm):
- Protein head: 641→512→256 (ESM2 640-dim + abundance scalar)
- Text head: 768→512→256

Both heads project into a shared 256-dim embedding space. Only the two MLPs are trained — ESM2 and BioBERT stay frozen throughout.

### 6. Training
`src/model/train.py` — InfoNCE contrastive loss (CLIP-style)

Hyperparameters:
- Batch size: 512, Epochs: 16, Max LR: 1e-5, Temperature: 0.07
- LR schedule: linear warmup (3%) → cosine decay
- Patient-level test split: 10–15 patients per cohort held out, never seen during training

Result (LUAD, 101 training patients, 16 epochs): loss 4.79 → 0.86

### 7. Multi-cohort scaling
All preprocessing steps extended to 8 cohorts: LUAD, BRCA, CCRCC, GBM, HNSCC, LSCC, OV, PDAC.

Multi-cohort checkpoint: `data/runs/luad_brca_ccrcc_gbm_hnscc_lscc_ov_pdac/checkpoint.pt`
Test patients: `data/test_patients_per_cohort.json` — 10 per cohort, reproducible with `random.seed(42)`

### 8. Evaluation

**8a. R@K** (`src/model/recall_at_k.py`)

For each (protein, patient) pair: text embedding → cosine similarity against all protein embeddings → rank of the correct protein.

| Experiment | R@1 | R@10 | R@50 |
|---|---|---|---|
| LUAD only (101 patients) | 61.50% | 94.02% | 98.22% |
| Multi-cohort (9 cohorts, all test patients) | 90.99% | 99.75% | 99.96% |

Random baseline: R@1 ≈ 0.01%

Full incremental scaling curve (R@K recomputed after adding each cohort, 1→9) saved to `data/scaling_results_v2.json`, computed via `src/model/run_experiments.py`. R@1 rises monotonically from 66.5% (LUAD only, this run's own checkpoint) to 90.9% (all 9 cohorts) — confirms the scaling hypothesis. Note: the 66.5%/95.4%/98.6% "LUAD only" numbers in that JSON come from a different checkpoint/test-split setup (`data/runs/luad/checkpoint.pt`, 10 held-out patients) than the 61.50%/94.02%/98.22% row above (`data/luad/checkpoint.pt`, 15 held-out patients) — both are valid but not directly comparable; don't mix them in the same table without noting the difference.

**Important — R@K measures something narrower than it looks like it does.** `recall_at_k.py` queries each protein with *its own* pre-cached true annotation text, which by construction starts with its own gene name (e.g. `"EGFR: receptor tyrosine kinase..."`). Near-100% R@K mostly proves the model can re-identify a protein from a description containing its own name — a closed-set self-identification task with a built-in shortcut, not evidence of general biological understanding. See **8d** below for the harder, shortcut-free test (pathway AUROC) and how the two numbers together tell the real story.

**8b. Query evaluation** (`src/model/query_evaluation.py`)

Fixed biological queries → mean percentile rank across all test patients.

Key findings:
- Collagen queries work very well: COL1A1 top 0.8%, COL1A2 top 0.9%
- Structural/ECM proteins generally good — model learned these clearly
- Functional groups weak: MTOR 98.3%, RPS3 73.3% — near random
- Root cause: model was trained on UniProt vocabulary, not generic biological query language

**8c. Pathway AUROC** (`src/evaluation/pathway_evaluation.py`)

~300 KEGG pathways as ground truth → AUROC measures how well the model ranks pathway members above non-members across all test patients.

First results (multi-cohort checkpoint, raw pathway names as queries):
- Mean AUROC: ~0.72–0.75 (random baseline = 0.50)
- Best: Mucin O-glycan biosynthesis (0.96), Arginine biosynthesis (0.95), Fatty acid biosynthesis (0.90)
- Cancer signaling: Cell cycle (0.71), cAMP signaling (0.69)
- Full results: `data/evaluation/pathway_auroc_results.csv`

**8d. Objective pathway selection + filtered AUROC** (`src/evaluation/pathway_final_choice.py`, `src/evaluation/pathway_final_auroc_evaluation.py`)

Problem: the ~20 hand-picked pathways originally planned for a "focused evaluation" (see section 9 of the 2026-06-28 notes below) were rejected by the professor as not scientifically defensible — manually curating a subset out of 320 candidates is selection bias, however well-intentioned the picks are.

Solution: replace pathway *picking* with pre-specified pathway *inclusion criteria*, applied identically to all 320 KEGG pathways and decided before looking at any AUROC results:
1. **Coverage filter (hard cutoff):** `mean_measured / kegg_total_genes >= 50%` — at least half of a pathway's KEGG member genes must actually be measured (non-NaN), on average across test patients. Excludes 75/320 pathways — mostly membrane receptors/GPCRs and low-abundance secreted signaling proteins (olfactory transduction, taste transduction, cytokine-receptor interaction), a known mass-spec detection blind spot rather than a flaw in the filter.
2. **Power filter (hard cutoff):** `min_measured >= 5` (matches `MIN_POSITIVES`, already used for AUROC stability elsewhere) — the *worst-covered* test patient must still have ≥5 measured pathway genes, so no patient is silently dropped from a pathway's AUROC computation.
3. **Annotation coverage (covariate, not a filter):** fraction of a pathway's genes with a real UniProt annotation (vs. the ~1,421 unannotated TrEMBL entries) — reported next to AUROC so a low score can be judged as a model failure vs. a UniProt data gap, but it does not gate inclusion.

Cohort-matched cancer-type pathways (Non-small cell lung cancer for luad/lscc, Breast cancer, Renal cell carcinoma, Glioma, Pancreatic cancer, Endometrial cancer) are flagged as a **pre-specified secondary analysis** — motivated by "these are the cohorts the model trained on," decided independent of how they score. HNSCC and OV have no direct KEGG cancer-type match.

**Results (9-cohort checkpoint, `data/evaluation/pathway_final_auroc_results.csv`):**
- 245 / 320 pathways passed both hard filters
- Mean AUROC = 0.573 (median 0.556, range 0.32–0.95)
- 79 / 245 pathways (32%) scored *below* the 0.5 random baseline — notably neurological/cardiac disease pathways with no obvious proteomic signature in cancer patients (Alzheimer disease 0.355, Arrhythmogenic right ventricular cardiomyopathy 0.333)
- Correlations: `coverage_fraction` r=+0.23, `annotation_coverage_fraction` r=+0.24, `kegg_total_genes` r=-0.37 — bigger/more diffuse pathways score worse, a quantitative confirmation of the "large heterogeneous pathways underperform" pattern first noticed in 8c
- **Cohort-matched secondary analysis:** mean AUROC = 0.473, *below* the overall 0.573 — Glioma 0.539, NSCLC 0.507, Pancreatic cancer 0.470, Renal cell carcinoma 0.429, Endometrial cancer 0.417. **Breast cancer was excluded from the evaluation set entirely** — its coverage (47.8%) fell just under the 50% cutoff, before AUROC was ever computed. This is the filter working as intended: it excludes even the most thesis-relevant pathway when the data doesn't support it, with zero regard for how the result would look.

**Methodological caveat — checkpoint confound:** comparing 0.573 (new, filtered, 9-cohort checkpoint) against the earlier 0.72–0.75 (8c, unfiltered, 8-cohort checkpoint) is misleading. When the *old* unfiltered results are restricted to the same 245 pathways, the mean is 0.605 — nearly identical to its own full-320-pathway mean (0.606). This shows **the filtering itself barely changes the aggregate number**; the ~3-point gap between 0.605 and 0.573 is attributable to the checkpoint version (8-cohort vs. 9-cohort/+UCEC), not to pathway selection. Rerun both evaluations on the same checkpoint before making any "filtering changed the result" claim in the thesis.

**8e. Natural-language query rewrites — two independent phrasing styles** (`src/evaluation/pathway_nl_queries.py`, `src/evaluation/pathway_nl_queries_compact.py`, `src/evaluation/pathway_nl_auroc_evaluation.py`, `src/evaluation/pathway_three_way_auroc_evaluation.py`)

Tests whether the low cohort-matched AUROC (0.473 mean, see 8d) is a query-phrasing problem (raw KEGG names are database jargon) or a genuine generalization limit. Same methodology as pathway selection: one fixed prompt template applied identically to all 245 pathways, generated via the Claude API (`claude-opus-4-8`) *before* any AUROC results exist — no per-pathway hand-tuning after seeing scores. Ground truth (gene membership) is unchanged in all conditions; only the query text fed to the text encoder differs.

**Condition 1 — explanatory sentence** (`pathway_nl_queries.py`): prompt asked for "a short natural-language description... the way a researcher would type it into a search box." Produced uniform "How X does Y" explanatory sentences — in hindsight, this is closer to the register of the *planned LLM-interpretation step* (Claude explaining retrieved proteins to a researcher, see "Planned tool" section) than the *query* register a researcher actually types to search. Kept anyway and reported honestly, since the prompt was locked before evaluation.

**Condition 2 — compact search-query phrase** (`pathway_nl_queries_compact.py`): a second, independently-motivated prompt asking for a compact 3-8 word noun phrase, no question, no explanation — designed to better match real query behavior (PubMed/GSEA-style keyword phrases), decided *before* seeing whether it would score better, to avoid the same selection bias risk as the first prompt.

**Results (`data/evaluation/pathway_nl_auroc_results.csv`, `data/evaluation/pathway_three_way_auroc_results.csv`):**

| | mean AUROC | median | below random (n/245) |
|---|---|---|---|
| raw KEGG name | 0.573 | 0.556 | 79 |
| explanatory NL | 0.603 | 0.588 | 53 |
| compact NL | 0.573 | 0.563 | 73 |

- Explanatory phrasing improved the aggregate; compact phrasing landed statistically identical to raw names (same mean, only 111/245 pathways improved vs. 153/245 for explanatory).
- **Redistribution, not uniform improvement, for explanatory phrasing:** correlation(raw_auroc, delta_explanatory) = -0.49 — pathways that scored well on the raw name (small, lexically distinctive biochemical pathways whose KEGG name shares vocabulary with UniProt annotations, e.g. Ribosome, Sulfur relay system, Glycolysis) lost the most ground when paraphrased away from that vocabulary; Ribosome dropped from 0.807 to 0.434, below chance. This is direct, quantified evidence that part of the original 0.573 mean AUROC was inflated by lexical shortcut-matching rather than genuine semantic generalization (same "name shortcut" limitation as 8a, now demonstrated a second way).
- **The two NL styles don't even agree with each other:** correlation(delta_explanatory, delta_compact) = only 0.31. Compact phrasing crashed "Nitrogen metabolism" (0.834 → 0.393) while barely moving it under explanatory phrasing, and vice versa for other pathways — query-phrasing effects are partly idiosyncratic per pathway, not fully predictable from one general theory.
- **Cohort-matched pathways (the pathways that matter most for the thesis):**

| | raw | explanatory | compact |
|---|---|---|---|
| Endometrial cancer (ucec) | 0.417 | 0.463 | 0.558 |
| Glioma (gbm) | 0.539 | 0.512 | 0.619 |
| Pancreatic cancer (pdac) | 0.470 | 0.581 | 0.518 |
| Renal cell carcinoma (ccrcc) | 0.429 | 0.514 | 0.461 |
| NSCLC (luad,lscc) | 0.507 | 0.530 | 0.446 |
| **mean** | **0.473** | **0.520** | **0.520** |

Both NL styles land on the identical 0.520 mean — but via completely different, inconsistent per-pathway routes (compact phrasing helps Glioma/Endometrial a lot but makes NSCLC *worse than the raw name*). Neither style closes the gap to the overall pool mean (~0.57–0.60); both remain in a weak 0.45–0.62 band.

**Conclusion:** two independently-designed phrasing styles were tested, and neither reliably closes the cohort-matched gap — this is now two pieces of evidence, not one experiment that could be a fluke of a particular prompt. Query engineering has real but unpredictable, non-generalizable effects on this task; it is not a substitute for the model actually learning more generalizable biological vocabulary. This justifies prioritizing GO-term augmentation next (see section 9) over further prompt iteration.

## Current state of ProteomIQ (as of 2026-07-07)

### What it can do
- Given a patient's protein abundance sample, rank proteins by semantic relevance to a natural language query
- Works well for queries that use UniProt-style vocabulary, and for small, lexically distinctive biochemical categories: "receptor tyrosine kinase", "component of the 60S ribosomal subunit", "collagen fibril assembly", Ribosome/Glycolysis/Sulfur-metabolism-type pathways (raw-name AUROC 0.8–0.95)
- R@K=61.5% on LUAD-only test set, 90.9%/99.75%/99.96% on the full 9-cohort model (random baseline ~0.01%) — proves the contrastive training objective worked, though pathway-level AUROC (mean 0.573, see Timeline 8d) shows R@K is partly inflated by a name-matching shortcut
- query_evaluation.py shows concrete examples: EGFR ranks top 2%, COL1A2 top 0.7%, RPL7 top 0.1% for matching queries

### What it cannot do yet
- Answer truly patient-specific questions reliably — ranking is currently dominated by protein identity (ESM2), not abundance variation; pure cosine similarity gives nearly the same ranked list for every patient. Worked through *why*, theoretically, in the 2026-07-07 notes: without a patient-varying text target, the contrastive loss has no incentive to use the abundance dimension at all. `activity_score` (inference-time, not learned) is the planned fix — not yet validated on real examples.
- Score well on the categories that matter most for the thesis's clinical framing — cohort-matched cancer pathways (Glioma, NSCLC, Pancreatic, Renal, Endometrial) score 0.42–0.62 across raw names and two independently-tried natural-language phrasings (Timeline 8e) — a genuine generalization limitation, not a query-phrasing artifact, since two different phrasing styles were tried and neither fixed it.
- Answer generic researcher questions ("what's driving this tumor?") — model was trained on UniProt annotations, not clinical reasoning language; the planned fix is the downstream Claude-API interpretation step (prompted, not fine-tuned), not the retrieval model itself.
- Classify cancer type or characterize what kind of patient a sample came from
- Work outside LUAD in the Streamlit app (not built yet)
- Say a protein is "overexpressed" — within-sample rank has no cross-patient reference

### How to explain it to a professor
*"ProteomIQ is a proof-of-concept that shows CLIP-style contrastive training works for proteomics data. Given a patient's protein abundance sample, the model ranks proteins by semantic relevance to a free-text query — for example, ranking EGFR and MET highest for 'receptor tyrosine kinase signaling.' Multi-cohort R@K=90.9% shows the model can discriminate its own training pairs almost perfectly, but that number is inflated by a name-matching shortcut — the harder, shortcut-free pathway-AUROC evaluation (mean 0.573, no gene names in the query) shows more modest, uneven generalization: strong on lexically distinctive biochemical pathways, weak on diffuse cancer-signaling pathways. We tested two independently-designed natural-language query rewrites to see if that weakness was just a phrasing problem — neither closed the gap on the cohort-matched cancer pathways, which is evidence the limitation is a genuine generalization gap, not a fixable prompt. The current retraining plan drops clinical description from the training text (fixing a train/inference format mismatch we identified) and adds GO-term vocabulary, while patient-specific ranking is handled explicitly at inference via `activity_score`, independent of what the embedding itself learns."*

### How it differs from GSEA
GSEA requires predefined pathway gene sets and tests statistical enrichment. ProteomIQ accepts any free-text natural language query against a specific patient's own measured proteins — a capability GSEA does not have at all, regardless of ProteomIQ's current accuracy. That said, GSEA is the more rigorous, validated tool for confirmatory analysis; ProteomIQ's role is hypothesis generation and exploratory analysis, not a replacement (see "Known limitations" above). The free-text advantage fully materializes once GO-term augmentation is done — until then, the model only works well for queries that closely match UniProt annotation language.

### Is ProteomIQ a useful tool? (honest assessment, 2026-07-07)
Two different senses of "useful," both worth stating plainly in the thesis discussion:

**As a research prototype:** yes, but scoped narrowly — useful for **hypothesis generation on well-covered biological questions**, not yet as a general-purpose exploration tool (contrast with CellWhisperer, which is built for open-ended whole-dataset exploration across many cells at once — a genuinely different, broader scope than ProteomIQ's one-patient-at-a-time protein retrieval) and explicitly not as a clinical decision tool. The comparison to make is against GSEA (the real alternative), not against a hypothetical perfect tool: GSEA cannot take a free-text question and rank a specific patient's measured proteins against it at all; ProteomIQ can, even with an AUROC profile that's strong in some categories (0.8–0.95) and weak in others (0.42–0.52, notably the clinically-central cancer pathways) — a noisy but real signal is still a legitimate aid for "here's what's worth investigating further," which is the honest, correct scope for this kind of tool.

### 10. Motivation: from "drop clinical" to "drop abundance too"
Dropping clinical description alone (`retrain-drop-clinical`) fixed a real train/inference text-format mismatch, but didn't close the generalization gap: pathway AUROC on the same 245-pathway evaluation set barely moved (with-clinical 0.5735 → no-clinical 0.5596, both still *with* abundance in the protein input) — if anything slightly worse. This motivated going further: drop abundance from training entirely, and move patient-specificity to a separate, inference-time mechanism (`activity_score`, see 10h) instead of trying to learn it into the embedding. This is the already-planned "abundance ablation," but working through it surfaced problems serious enough to make it the thesis's main architecture rather than a side experiment.

### 10a. The duplicate-pairs problem (discovered before training)
Once abundance is also dropped, `protein_emb`/`text_emb` become fully patient-invariant — the same protein across many patients becomes a literally identical training row. Deduplicating within one cohort alone already shows the scale: LUAD collapses from 1,052,388 rows (with abundance) to 11,482 (one row per protein, no abundance) — a ~92x reduction. Measured directly (not estimated): summed across all 9 cohorts, per-cohort dedup still leaves 98,029 total rows against only 15,733 truly unique proteins — a **6.23x** cross-cohort duplication factor, with 6,892 proteins (44%) present in literally all 9 cohorts. Exact duplicate rows landing in the same InfoNCE batch create a false-negative problem — the loss demands `sim(protein_A, text_A) > sim(protein_A, text_B)` even when `text_A == text_B` by construction, which is mathematically impossible to satisfy and injects contradictory gradient noise. Decision: deduplicate globally across cohorts, not per-cohort.

### 10b. Verifying cross-cohort identity before deduping
Checked empirically before assuming it was safe to dedupe: ESM2 embeddings are **bit-identical** across cohorts for the same protein (deterministic function of sequence, frozen model) — confirmed exactly on a sample of shared proteins, zero max-abs-difference. BioBERT/UniProt-text embeddings are identical for 95.3% of proteins shared across all 9 cohorts, but **4.7% (325/6,892) genuinely diverge** — not a bug, but because UniProt's own annotation text was revised between different cohorts' `fetch_uniprot.py` run times (concrete example: ARF5's annotation gained a sentence about mTORC1 regulation between the `luad/brca/ccrcc/gbm` batch and the later `hnscc/lscc/ov/pdac/ucec` batch). Decision: dedup keeps whichever cohort's copy is encountered first, deterministically — and this 95.3%/4.7% split is reported honestly as a small, quantified data-quality footnote rather than building logic to guess which annotation is "more current."

### 10c. Global, protein-level train/validation/test split (not patient-level)
Once there's no patient-varying signal left at all, a patient-level held-out split stops being meaningful — a held-out patient's proteins were already seen (identical embeddings) via other training patients, so evaluating on them measures memorization, not generalization. Fix: exclude held-out proteins from **every** cohort, globally, not just one. `src/model/protein_train_validation_test.py` builds a reproducible split (`random.seed(42)`, shuffle-then-slice) over the union of all cohorts' usable proteins (15,733 total) → 80% train (12,587) / 10% validation (1,573) / 10% test (1,573), saved to `data/protein_splits.json` as `{"validation": [...], "test": [...]}` (train is implicit — everything else). A validation split (not just train/test) was added specifically because this retrain introduces a new hyperparameter decision (epoch count, see 10e) that has to be made without touching the test set — same principle as the project's existing patient-level test split, applied one level deeper.

**External validation:** found that ProteinCLIP (a real published contrastive protein–text model) uses this same protein-level train/val/test design for exactly this reason. Also worth noting: once abundance is dropped, this architecture's Stage 1 (protein sequence embedding ↔ functional text, no per-sample dimension) structurally converges onto ProteinCLIP's own primary design — not a stripped-down compromise, but landing on an established pattern from the literature.

### 10d. Implementation
- **`src/model/dataset.py`** — `ProteomicsDataset` gained `use_abundance: bool` and `held_out_protein_ids` / `restrict_to_protein_ids` parameters. When `use_abundance=False`, it builds one **flat, global** `protein_id → (esm2_vec, text_vec)` table merged across all cohorts (no `cohort_idx`/per-cohort bookkeeping at all for this path — only the `use_abundance=True` path keeps the original per-cohort/per-patient structure, since abundance genuinely is patient-specific there). Verified: with-abundance LUAD is unaffected (still exactly 1,052,388 pairs, no regression); global no-abundance dedup across all 9 cohorts gives 12,574 training rows after held-out exclusion (15,733 − 3,146 held out ≈ 12,587 expected; the small gap is a handful of held-out proteins that were never actually measured in any training patient to begin with).
- **`src/model/train_protein_level.py`** — a dedicated, standalone training script, not a flag bolted onto `train.py` — no patient-level concepts anywhere in it. `torch.manual_seed(42)` plus a seeded `DataLoader` generator (added after discovering that *unseeded* runs made epoch-count comparisons meaningless — identical `--epochs` values gave different results run to run, purely from random weight initialization and batch shuffle order, independent of the `random.seed(42)` already used elsewhere for data splitting — a different RNG, in a different library, doing a different job). `--epochs` is required with no default, forcing a deliberate choice. Saves both `checkpoint.pt` (latest epoch) and `checkpoint_best.pt` (lowest `val_loss` epoch, tracked automatically every epoch), with `val_loss`/`epoch`/`total_epochs` embedded in the checkpoint file itself for later cross-run comparison.

### 10e. Epoch count methodology
Mechanical reason the old epoch count (16) doesn't transfer: `steps_per_epoch = dataset_size ÷ batch_size`. Old multi-cohort dataset (~13M rows) → ~25,391 steps/epoch → ~406,000 total steps over 16 epochs. New deduped dataset (~12,574 rows) → ~25 steps/epoch → only ~400 total steps at the same "16" — nowhere near enough.

A second confound was found while comparing epoch counts: `get_cosine_schedule_with_warmup`'s warmup/decay shape is defined relative to `total_steps = epochs × steps_per_epoch`, so the *same nominal epoch number* lands at a different point in the learning-rate curve depending on the chosen `--epochs` total (e.g. epoch 855 = 42.75% through a 2000-epoch schedule vs. 85.4% through a 1001-epoch schedule — a different phase of decay, hence different loss). Combined with the initially-missing random seed, this explained several confusing, seemingly-inconsistent results before both issues were fixed.

**Controlled comparison, after fixing the seed** (identical data, identical hyperparameters, only `--epochs` varies):

| Epochs | Best val_loss | At epoch |
|---|---|---|
| 500 | 2.7180 | 496/500 |
| 1000 | 2.5235 | 881/1000 |
| 1500 | 2.5214 | 922/1500 |
| 2000 | **2.5172** | 804/2000 |

Clear diminishing returns (500→1000 a real ~7.2% improvement; 1000→1500→2000 only ~0.25% further) confirms genuine convergence rather than an artifact of a lucky/unlucky seed. The 2000-epoch run's epoch-804 checkpoint was promoted to `checkpoint_no_abundance_best.pt`.

**Why training loss plateaus around 0.75–1.58 here vs. ≈0.08 in the old with-abundance model:** not a sign of a worse-solved task. The old multi-cohort dataset's ~826x per-unique-protein duplication (patient-repeat × cross-cohort repeat), reinforced over 16 epochs, gave each unique protein–text mapping roughly **13,200 effective exposures** — versus this deduped model's exposure count equaling its epoch count directly (1,000–2,000). The old, much lower training loss reflects extreme redundancy-driven memorization opportunity, not deeper learning — a further, now-quantified instance of the project's existing "name shortcut" concern.

### 10f. Protein-level R@K (`src/model/recall_at_k_protein_level.py`)
No patient dimension exists in this model, so this loops over held-out **test proteins** directly (not patients), ranking each one's own text against a realistic **mixed** candidate pool of all proteins — train + validation + test, ~15,718 total — not a closed pool of only-test-proteins, mirroring what a researcher's real uploaded sample would actually contain (mostly familiar proteins, a few genuinely novel ones).

**Result:** R@1 = 19.45%, R@10 = 35.86%, R@50 = 49.52% (1,573 test proteins against 15,718 candidates; random baseline for this pool ≈ 0.0064% / 0.064% / 0.32% respectively — actual results are ~150–3,000x above chance).

**Important framing — this is not directly comparable to the old multi-cohort R@1 = 90.9%.** That number was measured on proteins the model *had* already seen (via other patients) — a closed-set memorization test, already flagged elsewhere in this file as inflated by the name shortcut. This new number is the first in the whole project to honestly measure zero-shot generalization to truly unseen proteins — lower not because something broke, but because it's finally measuring the harder, more meaningful thing.

### 10g. Protein-level pathway AUROC (`src/evaluation/pathway_auroc_protein_level.py`)
Reuses the existing objective pathway selection (the same 245 pathways passing `pathway_final_choice.py`'s coverage/power filters). For each pathway, computes two AUROC scores over the same ~15,718-protein pool:
- `overall_auroc` — standard AUROC, all pathway members (train + validation + test) count as positives.
- `test_only_auroc` — positives restricted to **test-set (never-trained) pathway members only**, evaluated against the full negative pool (train/validation *non-members* stay in as negatives; train/validation *members* are dropped from the calculation entirely) — isolates whether real generalization exists, independent of memorized train/validation members inflating the aggregate.

**Results:** overall mean AUROC = **0.6074** (n=245); test-only mean AUROC = **0.5836** (n=179 pathways with ≥5 test-set positives). The gap between the two is small (~0.024) — evidence the overall score isn't primarily propped up by memorized proteins; genuinely novel proteins are still placed correctly relative to pathway concepts, just modestly worse than the full-pool average.

**Comparison to prior with-abundance pathway AUROC, same 245-pathway set:** old 8-cohort checkpoint = 0.605, old 9-cohort with-clinical = 0.5735, old 9-cohort no-clinical = 0.5596. This new protein-level model's overall AUROC (0.6074) is comparable to, or slightly better than, all three — dropping abundance and rebuilding the architecture cleanly did **not** cost biological/pathway understanding, while also being the first version of this evaluation that can honestly claim to test genuine generalization at all.

### 10h. Architecture reframing: three explicit stages
This whole ablation exists to support a specific architectural decision, restated explicitly:
- **Stage 1 (this section)** — a clean, patient-invariant protein-function embedding: ESM2 sequence + UniProt annotation text, structurally similar to ProteinCLIP's own design.
- **Stage 2 (planned, not yet validated)** — `activity_score = cosine_similarity(query, protein_embedding) × abundance_rank`, applied at **inference time** using the specific patient's own raw abundance values. This is where patient-specificity actually enters — without requiring abundance to have been learned into the embedding at all.
- **Stage 3 (planned)** — Claude API interpretation layer: retrieved proteins + abundances + UniProt text → natural-language biological hypotheses, for the researcher-facing chat interface.

This resolves the "abundance-incentive" theoretical finding from the 2026-07-07 notes: since text no longer varies per patient, InfoNCE has no incentive to use the abundance dimension during training — which is fine specifically *because* Stage 2 recovers patient-specificity independently and post-hoc, rather than requiring it to be learned.

### 10i. Relationship to prior (patient-level) work
Explicit framing decision for the thesis: the original patient-level, with-abundance work (LUAD baseline, multi-cohort scaling, R@K, pathway AUROC pre/post clinical-drop, two NL query rewrite experiments) is **not discarded** — it becomes the ablation baseline this section's results are compared against, i.e., direct evidence for *why* abundance was moved out of training and into `activity_score` instead. The protein-level architecture in this section is the thesis's main, final direction going forward.

### 10j. `activity_score` evaluation validity problem (2026-07-12) — found before building any evaluation
Before empirically validating `activity_score = cosine_similarity(query, protein_embedding) × abundance_rank`, worked through what a *valid test* for it would even look like — and found that the obvious approach (AUROC against static KEGG pathway membership, the same ground truth used everywhere else in this file) is invalid for this specific method, not just imperfect. Pathway-membership AUROC rewards a ranking for recovering **every** true member regardless of whether that protein is actually expressed in a given patient. `activity_score` is *deliberately designed* to demote a true member that has low abundance in that patient — that is the entire point of multiplying by abundance. Grading it against static membership would penalize the model for doing exactly what it was built to do. A real flaw in the proposed evaluation, not a misunderstanding of the metric.

**Resolution — redesign the mechanism, not just the test.** Abundance's actual role isn't prediction — a patient's abundance value is already known, measured data, nothing needs to be predicted — it's *annotation*. Replaced the single blended `activity_score` multiplier with a two-step **retrieve-then-annotate** design, formalizing what 10h had sketched only loosely:
- **Stage 1 (semantic retrieval, unchanged, patient-invariant):** rank all proteins by `cosine_similarity(query, protein_embedding)`, take a **wide** top-N candidate pool (N=20 turned out to be far too narrow — see 10k). Nothing here depends on abundance, so a true pathway member can never be excluded from the candidate pool just for being lowly expressed in one particular patient.
- **Stage 2 (patient-specific annotation, new):** for a chosen patient, attach their real rank-normalized abundance percentile to each of Stage 1's candidates (or "not detected" if NaN). Never adds or removes candidates from Stage 1's list — only labels them.

This also cleanly separates what each stage needs to be validated against: Stage 1's quality is exactly what the existing pathway AUROC / recall@K infrastructure already measures (no new evaluation needed); Stage 2 is a direct data lookup, not a learned model, so it isn't — and shouldn't be — subjected to the same kind of ground-truth ranking test.

### 10k. Stage 1+2 implementation and spot check (`src/model/retrieve_and_annotate.py`)
Implements the redesigned two-step pipeline: live BioBERT query encoding → `text_head` → cosine similarity against all ~15,718 protein embeddings (`checkpoint_no_abundance_best.pt`) → top-N candidates (Stage 1) → per-patient abundance percentile lookup from `data/{cohort}/rank_normalized_proteomics.csv` (Stage 2). Optional KEGG ground-truth check built in: if `--query` is a literal KEGG pathway name (via `gseapy`), the script prints how many of that pathway's true members appear in the top-N — lets Stage 1 be spot-checked against real ground truth instead of eyeballing free-text query results with no verifiable answer key.

**Spot check, 3 highest-AUROC pathways (Biosynthesis of unsaturated fatty acids 0.9757, GPI-anchor biosynthesis 0.9686, Glyoxylate and dicarboxylate metabolism 0.9674), patients 11LU013/11LU016:**
- At `--top-n 20`: only 2/27 true members found for the fatty-acid pathway — looked broken, but is mathematically expected, not a bug: `mean_rank_of_positives ≈ (1 − AUROC) × pool_size ≈ 383` for that pathway, so top-20 (top 0.13% of the ~15,718-protein pool) is far narrower than what a 0.9757 AUROC actually promises (top ~2.4% on average). **AUROC is a global/average measure, not a top-K precision guarantee** — this directly motivated building a dedicated top-K metric (10l) instead of relying on manual top-20 inspection.
- At `--top-n 200`: fatty-acid pathway 13/27 (48%), GPI-anchor 17/26 (65%), glyoxylate/dicarboxylate 8/30 (27%). Despite near-identical AUROC for the latter two (0.9686 vs. 0.9674), top-200 concentration differs by more than 2x. Traced to the **name-shortcut pattern already documented elsewhere in this file**: GPI-anchor's members mostly share a `PIG*` name prefix and near-identical UniProt annotation vocabulary (14 of 21 `PIG*` genes recovered) — easy for a text-trained model to cluster. Glyoxylate/dicarboxylate's 30 members have no shared naming convention (`ACAT`, `ACO`, `CAT`, `DLD`, `MDH`, `SHMT`...) despite being biochemically related, and cluster far less tightly even at similar AUROC. A third, independent reproduction of the name-shortcut limitation (after 8a/R@K and 8e/NL-query-rewrites), this time surfaced via AUROC-vs-concentration divergence rather than query phrasing.

### 10l. Protein-level pathway recall@K (`src/evaluation/pathway_recall_at_k_protein_level.py`)
Built directly in response to 10k's finding that AUROC doesn't predict top-K concentration. Same pre-selected 245-pathway set and candidate pool as `pathway_auroc_protein_level.py`; for K ∈ {100, 200, 400}, computes `recall@K = (true members found in top K) / (total true members)`, both `overall` (any split counts as a hit) and `test_only` (only never-trained members count as hits, same generalization-vs-memorization logic as `test_only_auroc`). Output: `data/evaluation/pathway_recall_at_k_protein_level_results.csv`.

**Results — considerably starker than mean AUROC (0.6074) suggested:**

| K | mean recall@K | median recall@K | pathways with zero hits |
|---|---|---|---|
| 100 | 3.2% | 0.5% | 115/245 (47%) |
| 200 | 5.2% | 1.7% | 73/245 (30%) |
| 400 | 8.3% | 3.4% | 40/245 (16%) |

The **median**, not the mean, is the honest summary here: for a typical pathway, essentially none of its true members appear even in the top 400 (top ~2.5% of the pool). The 3 pathways spot-checked in 10k were the literal top-3-by-AUROC out of all 245 — not representative; this run is the first to show what a *typical* query actually looks like in practice, and it is much weaker.

**Diagnosed why so many pathways score exactly zero even at K=400 — two distinct causes, not one:**
1. **Most cases (mean AUROC 0.496 for zero-recall@400 pathways vs. 0.629 for nonzero ones):** AUROC itself is at or below the random baseline for these pathways (`Regulation of lipolysis in adipocytes` 0.265, `PPAR signaling pathway` 0.342, `Oxytocin signaling pathway` 0.356, `Dopaminergic synapse` 0.363, ...) — the model has no usable signal for them at all; zero recall@K is just what AUROC ≈ 0.5 looks like concretely, not a separate failure mode.
2. **A smaller group has good-to-high AUROC but very few true members** (`Sulfur metabolism` AUROC 0.85 with only 10 members, `SNARE interactions in vesicular transport` 0.78 with 41, `Nitrogen metabolism` 0.72 with 16): random-chance expected hits in the top 400 for a 10-member pathway is `10 × 400/15,718 ≈ 0.25` — under one expected hit before even considering model quality. A handful of true members ranked systematically better-than-average (driving a high AUROC) can still miss an arbitrary top-K cutoff entirely. A small-sample statistical artifact, not a model failure — same underlying reasoning as the `MIN_POSITIVES` stability filter used elsewhere in this evaluation.

**Why this matters more than one more number:** mean AUROC (0.6074) reads as "moderately better than random, plausible." Median recall@200 (1.7%) shows the *practical* picture — what a researcher would actually see through Stage 1's real top-N candidate list — is far weaker for most queries, and only the small subset of lexically-distinctive pathways (the name-shortcut winners) are currently usable end-to-end. This is the strongest, most quantified justification yet for prioritizing the GO-term augmentation retrain over further evaluation refinement.

### 10m. Gene-name masking ablation — direct test of the name-shortcut hypothesis (2026-07-13)
Every prior piece of evidence for the "name shortcut" (8a's R@K-vs-AUROC gap, 8e's two failed NL query rewrites, 10k's AUROC-vs-recall@K divergence) was indirect or inference-side — none directly intervened on the training text itself. This does: strip the leading `"{Gene}: "` prefix (fetch_uniprot.py always builds `Annotation` as `gene + ': ' + function text`, so this is an exact, deterministic string operation) from every protein's annotation before embedding, and retrain with identical protocol to the existing best checkpoint (2000 epochs, seed 42, same 9 cohorts) — the only variable changed is which BioBERT embeddings feed the text side.

**Implementation:** `embed_biobert.py` gained a `--mask-gene-names` flag, writing to `biobert_embeddings_masked.h5` alongside (not overwriting) the original per cohort — confirmed the prefix was stripped from effectively 100% of annotations in every cohort (11,213/11,214 in BRCA; the single miss is presumably a blank gene field). `dataset.py` and `train_protein_level.py` gained a `biobert_filename` parameter so masked and unmasked pipelines coexist. New checkpoint: `data/runs/.../checkpoint_no_abundance_masked_e2000_best.pt`.

**Results — every downstream generalization metric improved, while training fit got *worse*:**

| Metric | Baseline (unmasked) | Masked | Δ |
|---|---|---|---|
| best val_loss | 2.5172 (epoch 804) | 2.5478 (epoch 705) | worse |
| AUROC overall | 0.6074 | 0.6264 | +0.019 |
| AUROC test-only | 0.5836 | 0.5952 | +0.012 |
| recall@100 (mean) | 3.2% | 4.38% | +1.18pp (+37% rel.) |
| recall@200 (mean) | 5.2% | 7.18% | +1.98pp (+38% rel.) |
| recall@400 (mean) | 8.3% | 10.97% | +2.67pp (+32% rel.) |

**Interpretation:** the worse training loss is expected — removing the gene name removes an easy loss-reducing signal InfoNCE previously exploited freely. That every shortcut-free evaluation metric improved anyway is the interesting result: some of the original checkpoint's training-loss advantage was propped up by a shortcut that didn't transfer to genuine generalization, not by deeper biological learning. This is the third, and first *experimentally confirmed via direct intervention* (rather than observed or inferred), instance of the name-shortcut finding.

**Caveat:** absolute numbers remain weak in practical terms — recall@200 mean of 7.18% still means the large majority of a typical pathway's true members don't appear in a realistic top-200 candidate list. Masking removes a confound; it does not solve the underlying generalization gap. Decision: fold gene-name masking into the baseline for all retrains from here on, since it is a free, consistently positive change with no observed downside.

### 10n. GO-term augmentation ablation — a negative result (2026-07-13)
Following 10m's plan, extended `fetch_uniprot.py` to extract GO Biological Process + Cellular Component term labels per protein (from the same UniProt idmapping response already being fetched, no new API call) and re-fetched `protein_annotations.csv` for all 9 cohorts. `embed_biobert.py` gained `--include-go-terms` (appends `"Biological process: {terms}. Cellular component: {terms}."` after the masked annotation, capped at `MAX_GO_TERMS_PER_CATEGORY = 10` per category, chosen in 10m's plan) and `--go-bp-only` (drops CC, see below). Trained with identical protocol to 10m (2000 epochs, seed 42, same 9 cohorts) on top of the masked-text baseline. New checkpoints: `checkpoint_no_abundance_masked_go_e2000_best.pt` (BP+CC) and `checkpoint_no_abundance_masked_go_bp_only_e2000_best.pt` (BP-only, see below).

**First result — training fit improved, but every shortcut-free metric regressed (the opposite pattern from 10m):**

| Metric | masked-only (10m) | masked+GO (BP+CC) | Δ |
|---|---|---|---|
| best val_loss | 2.5478 (epoch 705) | 2.354 (epoch 830) | better |
| self-ID R@1/10/50/100 | 18.50/36.11/48.70/55.69 | 18.98/36.75/51.72/60.19 | better |
| pathway AUROC overall | 0.6264 | 0.5823 | −0.044 |
| pathway AUROC test-only | 0.5952 | 0.5533 | −0.042 |
| pathway recall@100/200/400 (overall) | 4.38/7.18/10.97% | 2.24/3.79/5.98% | ≈ halved |
| pathway recall@100/200/400 (test-only) | 3.03/5.24/7.64% | 1.48/2.51/4.49% | ≈ halved |

**Diagnostic 1 — truncation.** `EGFR`'s masked annotation alone tokenizes to 528 tokens, already past BioBERT's 512-token cap *before* any GO terms are appended — its masked and masked+GO embeddings are byte-identical (max abs diff = 0.0), confirmed directly. Quantified across all of LUAD's 11,513 proteins: 89.5% get the full GO-term effect, 4.3% get a partially-truncated effect, and **6.2% get zero effect** — disproportionately likely to be well-studied, clinically relevant proteins (long UniProt annotations correlate with research attention). A real caveat, but too small a fraction to explain a regression of this size on its own.

**Diagnostic 2 — GO_Cellular_Component genericness.** Measured directly against `protein_annotations.csv`: `cytosol` appears on 37.1% of all proteins, `nucleus` on 32.8%, `cytoplasm` on 32.6% — CC terms are largely shared boilerplate, not distinguishing signal. GO_Biological_Process terms are somewhat more specific but still generic at the top (`DNA-templated transcription` at 11.0%). Hypothesis: this boilerplate dilutes the mean-pooled BioBERT training target, explaining why self-ID R@K went up (shared vocabulary is easy to pattern-match back to) while pathway AUROC went down (that vocabulary carries no query-relevant signal).

**Diagnostic 3 — length/format mismatch, tested via two independent NL query styles.** A competing hypothesis: `text_head` is trained only on long GO-augmented text, then queried at eval with a bare 1-4 word raw pathway name — a train/eval format gap unrelated to genericness. Tested by re-running pathway AUROC with natural-language query rewrites (both the "explanatory" and "compact" styles reused from 8e, recovered from git history) instead of raw KEGG names, for both masked-only and masked+GO:

| Checkpoint | Raw KEGG name | Explanatory NL | Compact NL |
|---|---|---|---|
| masked-only | 0.6264 / 0.5952 | 0.6368 / 0.6040 | 0.6334 / 0.5967 |
| masked+GO (BP+CC) | 0.5823 / 0.5533 | 0.6011 / 0.5894 | 0.5946 / 0.5626 |
| **Δ (masked+GO − masked-only)** | **−0.044** | **−0.036** | **−0.039** |

*(format: overall AUROC / test-only AUROC)*. NL phrasing generically helps both checkpoints a little (consistent with 8e), but the masked-only vs. masked+GO gap barely moves regardless of query phrasing — **ruling out length/format mismatch as the primary driver**. This pointed back to diagnostic 2 (genericness) as the better-supported explanation, motivating a direct test.

**Follow-up experiment — BP-only, dropping the generic CC terms:** if genericness were the primary driver, removing CC should recover most of the gap. It did not — BP-only scored **worse** than the full BP+CC version, not better:

| Metric | masked-only | masked+GO (BP+CC) | masked+GO (BP-only) |
|---|---|---|---|
| best val_loss | 2.5478 | 2.354 | 2.4242 |
| self-ID R@1/10/50/100 | 18.50/36.11/48.70/55.69 | 18.98/36.75/51.72/60.19 | 18.79/38.03/52.17/58.15 |
| pathway AUROC overall | 0.6264 | 0.5823 | **0.5579** |
| pathway AUROC test-only | 0.5952 | 0.5533 | **0.5268** |
| pathway recall@100/200/400 (overall) | 4.38/7.18/10.97% | 2.24/3.79/5.98% | 2.13/3.86/6.35% |
| pathway recall@100/200/400 (test-only) | 3.03/5.24/7.64% | 1.48/2.51/4.49% | 2.50/4.06/6.18% |

**Interpretation.** Genericness (diagnostic 2) turned out not to be the primary driver either — removing the generic half of the added text made the shortcut-free metric worse, not better, even though self-ID R@K held up fine. The pattern that actually holds across both GO variants: **any** added GO text — generic (CC) or more specific (BP) — improves training loss and self-ID R@K while hurting pathway AUROC/recall@K. This is the mirror image of 10m: masking *removed* an easy self-identification shortcut and that *helped* generalization; GO augmentation *adds* extra protein-distinguishing tokens that apparently function as a new self-ID shortcut, regardless of vocabulary genericness, without transferring to genuine pathway-level generalization. A fourth independent demonstration of the name/shortcut pattern already documented in 8a, 8e, and 10k/10l — this time surfaced via a failed augmentation attempt rather than an evaluation-design insight.

**Decision:** GO-term augmentation, as implemented (raw term concatenation, either BP+CC or BP-only), does not help and measurably hurts shortcut-free generalization. Reverting to masked-only (10m) as the working baseline. Not pursuing further GO-term variants (e.g. frequency-filtering, reordering) given the consistency of the negative result across two independently-motivated variants and the 2-month timeline — this is treated as a resolved, reported negative result rather than an open thread.

**Incidental fixes made during this ablation** (kept regardless of the GO-term outcome, since they're real bugs independent of it): `recall_at_k_protein_level.py` previously had no `--biobert-filename` parameter and silently defaulted to the plain unmasked text file regardless of which checkpoint was being evaluated — harmless for the one baseline run it had been used for, but would have silently fed a masked/GO-trained `text_head` out-of-distribution input had it been reused as-is. `pathway_auroc_protein_level.py` and `pathway_recall_at_k_protein_level.py` saved results to a fixed filename regardless of checkpoint, so each new run silently clobbered the previous run's CSV — now suffixed by checkpoint stem. New file `pathway_nl_auroc_protein_level.py` adapts the NL-query-rewrite methodology (originally built for the old patient-level, with-abundance architecture in `pathway_nl_auroc_evaluation.py`) to the current protein-level, no-abundance architecture — the old script's `build_protein_index` concatenates a 641-dim (ESM2 + abundance) vector, structurally incompatible with the current 640-dim, abundance-free `protein_head`.

### 10o. LLM-fusion augmentation — built and spot-checked, paused on budget (2026-07-13)
Motivation: 10n's raw GO-term concatenation failed twice (BP+CC, BP-only) — hurt pathway AUROC/recall@K despite helping training loss/self-ID R@K. One untested explanation: the added text was a bare semicolon-separated term list ("Biological process: term; term."), a completely different register from both the base UniProt prose and every eval query style tried (raw KEGG name, explanatory NL, compact NL) — so the model may have learned to treat it as noise rather than content, independent of whether the underlying facts were generic or specific. This motivated testing a differently-*structured* augmentation: instead of concatenating raw GO terms, use an LLM to fuse the masked UniProt annotation + GO_BP + GO_CC facts into one coherent natural-language paragraph per protein — same underlying facts as the BP+CC variant, but in prose register matching the rest of the corpus.

**Built:** `src/embeddings/textual/fuse_protein_text_llm.py`. Step 1 (always run): builds one global deduped protein table across all 9 cohorts — done *before* generation (not after, like the rest of the pipeline) so the same protein is never fused twice from two cohorts' slightly-diverged annotation text (see 10b's 4.7% divergence finding). Step 2: one fixed prompt per protein (`claude-sonnet-5`, explicit "use only the given facts, don't invent, don't mention the gene name, no bullet points/labels" instructions), with `--sample N` (prints + saves `data/protein_fused_text_sample.csv`, no full run) and `--full` (all ~15,715 proteins → `data/protein_fused_text.csv`) modes.

**Quality check (`--sample 10`):** reviewed each fused paragraph against its source facts side-by-side. Found one real prompt-compliance slip: for SAG, the source text says "binds to ... RHO" (another protein's bare gene symbol); the fused text expanded it to "rhodopsin" — technically outside knowledge not in the input, violating the letter of the "use only given facts" instruction. Judged low-risk on reflection: it doesn't add or change any biological claim (RHO deterministically = rhodopsin), and — more importantly for this project's specific shortcut concern — it doesn't leak the *masked subject's own* identity (SAG's own name stays masked); it only spells out a *different*, already-unmasked, already-present cross-referenced gene symbol, a category of information that has been present in every training-text variant since the original baseline. Decision: left the prompt as-is rather than tightening and re-validating — not worth the extra cost/cycle for a single low-risk instance in 9/10 clean.

**Cost estimate (measured, not guessed):** sampled real token counts via `count_tokens` — avg 612 input / 217 output tokens per call (much larger than the 245-call pathway-query-rewrite job's per-call cost, since this prompt carries the protein's full annotation + GO terms as input and a full paragraph as output, not a short pathway name → one-sentence rewrite). Full run (15,715 calls): **~$53 direct at claude-sonnet-5 intro pricing** ($2/$10 per MTok, active through 2026-08-31), or **~$27–40 via the Batch API** (50% off, and better suited to this volume than the 245-call job where batching wasn't worth the queue latency).

**Status: paused, not a decision against the approach — a budget constraint.** Available Claude API credit balance is $4, far short of the ~$25–55 needed. Nothing is lost by pausing: the dedup table logic, prompt, and quality-check tooling are done and committed; resuming later is just running `--full` (or building the Batch API variant first, which the cost estimate suggests is worth doing at this volume) once credit is available.

**To resume:** `uv run python src/embeddings/textual/fuse_protein_text_llm.py --full` (or build a Batches-API version first — recommended given the volume), then: embed the fused text globally (one BioBERT embedding per unique protein, not per cohort — analogous to the dedup-before-generation choice in Step 1), train with identical protocol to 10m/10n (2000 epochs, seed 42, same 9 cohorts), then run the full eval suite (self-ID R@K, pathway AUROC raw + both NL styles, pathway recall@K) and compare against masked-only (10m: AUROC 0.6264/0.5952, recall@100/200/400 4.38/7.18/10.97%) and the two failed GO variants (10n).

### 10p. Basic bidirectional cross-modal retrieval eval — closed test-set (2026-07-13)
Built `src/evaluation/cross_modal_eval.py`: the standard CLIP-style retrieval sanity check — distinct from every other R@K-based eval in this document. `recall_at_k_protein_level.py` (10f) uses a mixed train+val+test candidate pool (realistic-deployment simulation) and only queries text→protein; this script instead restricts **both** the query set and the candidate pool to the closed protein-level test split (`data/protein_splits.json`, ~1,573 proteins) and computes R@1/5/10/50 in **both directions** (text→protein, protein→text) — the closed-set, bidirectional protocol standard CLIP papers report (Flickr30k/COCO-style), and a same-pool basis for comparing the three text-variant checkpoints directly.

**Results (2000-epoch checkpoints, identical protocol, only the text variant differs):**

| Checkpoint | Pool | T→P R@1/5/10/50 | P→T R@1/5/10/50 |
|---|---|---|---|
| unmasked | 1,573 | 33.38/49.33/56.20/72.60 | 33.50/50.16/56.71/72.41 |
| masked | 1,573 | 32.99/49.65/55.24/71.84 | 35.41/51.11/57.09/71.46 |
| masked+GO (BP+CC) | 1,570 | 33.89/53.18/60.13/76.50 | 35.35/52.93/60.32/75.80 |

**Finding 1 — masking has no visible effect on this metric.** Unmasked and masked land within ~1pp of each other at every K, despite masking clearly improving pathway AUROC (0.6074 → 0.6264, 10g/10m) — this metric is not sensitive to the same thing pathway AUROC is.

**Finding 2 — masked+GO wins this metric outright, the opposite of the pathway-level ranking.** masked+GO beats both other checkpoints at every K past R@1 (R@50: 76.50% vs ~72%), while 10n already showed masked+GO is clearly *worse* on pathway AUROC (0.5823 vs 0.6264) and pathway recall@100 (roughly halved: 2.24% vs 4.38%). Not a contradiction in the data — a **fifth demonstration of the name/shortcut pattern** (after 8a, 8e, 10k/10l, 10n): this eval's closed 1,570–1,573-protein pool is structurally a self-identification task (find your own unique text/embedding among a small closed set of candidates), and extra protein-distinguishing text (GO terms) makes that easier without transferring to open-vocabulary pathway-level generalization — exactly like GO terms already did for self-ID R@K in 10n.

**Why this belongs at the start of the Experiments section:** it's the standard, literature-recognizable CLIP retrieval check, and it shows the contrastive objective clearly works (all three checkpoints far above the ~0.06% random baseline for a ~1,570-protein closed pool). Its disagreement with pathway AUROC on checkpoint ranking is the intended pivot into the harder, shortcut-free evaluation — not a loose end to resolve or hide, mirroring how 8a (R@K) → 8c/8d (pathway AUROC) was already structured for the patient-level work.

Decision: masked-only (10m) remains the working baseline; not pursuing further GO-term variants.
- **LLM-fusion augmentation (10o) — built, spot-checked, paused on budget.** Not a reconsideration like the paraphrase idea below — this is queued and ready, blocked only by API credit ($4 available, ~$25–55 needed). Resume via `fuse_protein_text_llm.py --full`, then embed/train/eval per 10o's "To resume" steps.
- **LLM-paraphrase augmentation (multiple variants per protein, targeting pair scarcity) — reconsider before pursuing.** The original plan (see 2026-07-07 notes) bundled this together with GO-term augmentation, conditioned on GO terms helping first (they didn't). The problem it targets — pair scarcity, 12,574 unique training pairs after global dedup (10e) — is real and independent of the GO-term result, so it isn't automatically ruled out. But it now needs its own justification rather than riding on GO-term augmentation's coattails, and 10n's finding (added protein-distinguishing text can function as a new shortcut rather than genuine signal) is a reason for caution, not just a green light — paraphrases risk the same failure mode if they mostly add surface variety without new biological content. Not started; needs a fresh decision given the 2-month timeline before committing engineering time. Distinct from 10o's single-fused-paragraph approach, which is about text *structure/register*, not pair-count diversity.
- LLM integration (Stage 3) proof-of-concept, per the already-existing plan, unchanged.

**As a bachelor's thesis contribution, independent of the model's absolute performance:** the methodology built across this work — objective, pre-registered pathway selection criteria instead of hand-picking (8d), two independently-designed natural-language query experiments reported honestly even where they didn't help (8e), a quantified demonstration of the name-shortcut limitation reproduced four separate ways (R@K vs. AUROC gap in 8a, NL query rewrites in 8e, AUROC-vs-recall@K divergence in 10k/10l, and the GO-term augmentation ablation in 10n), catching and fixing an invalid evaluation design before running it rather than after (10j), and building a new metric specifically because an existing one was masking the real picture (10l) — is itself a legitimate, rigorous scientific contribution. A thesis that honestly reports what works, what doesn't, and why is stronger than one that oversells a higher raw metric. The recall@K result (median 1.7% at K=200) is a genuinely weak practical number and should be reported as one — but the process that surfaced it, rather than settling for the more flattering mean AUROC, is the actual point of the exercise, and it directly motivated the GO-term augmentation attempt (10n) — itself now a well-diagnosed negative result rather than an unaddressed limitation, which is a genuine finding in its own right, not a dead end.

## 11. Full human proteome + homology-aware split (2026-07-15) — designated start of the thesis narrative

**Everything above this line (sections 1–10p) stays in the document and stays true, but is now framed as prior/foundational work** — the patient-level baseline, the move to protein-level, and the masking/GO-term/LLM-fusion ablations that led here. This section marks a deliberate decision: from here on is what gets written up as the thesis's main methodology and results, chosen at this point rather than earlier because everything before it was a sequence of exploratory pivots (clinical+abundance → drop clinical → drop abundance → mask names → GO-terms (failed)) needed to arrive at a defensible design, not the design itself. Timeline: today is 2026-07-15; hand-in is 2026-10-10 (~87 days).

### 11a. Motivation: two problems with the section-10 protein-level baseline, fixed together deliberately
1. **The protein universe was arbitrarily restricted.** Training only used the ~15,733 proteins that happened to be detected across the 9 CPTAC cohorts' mass-spec runs — a technical artifact of one specific measurement pipeline, not a principled boundary. Stage 1 (section 10h) never uses abundance at all, so it never needed measurement to have happened in the first place.
2. **The train/val/test split had no homology control.** `protein_train_validation_test.py` (10c) was pure random over individual proteins — a near-identical paralog could land in both train and test, inflating apparent generalization. Checked directly against a published protein-CLIP paper (ProtET, "Multi-Modal CLIP-Informed Protein Editing") while researching whether pathway AUROC was the right eval metric: ProtET has the same gap (no homology-aware splitting), which is a caution, not a precedent to copy.

**Explicit design discipline:** these two fixes are deliberately built as *one* clean protein universe with *one* valid split over it — not a two-tier system where "measured" proteins are eval-eligible and everything else is train-only bonus data. An earlier draft of this plan did propose that two-tier design; it was rejected mid-planning specifically because it would have bundled "more data" and "a fairer split" into one retrain with no way to attribute a result to either cause — the same one-variable-at-a-time discipline used everywhere else in this document (mask before GO-terms, drop-clinical before drop-abundance).

### 11b. Fetching the complete reviewed human UniProt proteome
`src/Textual/fetch_full_human_proteome.py` — new script, structurally different from `fetch_uniprot.py` (which maps a cohort's own ENSP list to UniProt records via the `idmapping` job/poll API). This instead queries UniProt's `search` API directly by `organism_id:9606 AND reviewed:true`, paginated via the `Link` header (same pagination pattern, different endpoint — no job/poll step needed, so much faster: full run completes in a few minutes).

**Per entry:** extracts UniProt accession, gene name, first `FUNCTION` comment (same `"{Gene}: {text}"` format as before — masking still happens later, only at `embed_biobert.py` time, unchanged), sequence, GO_Biological_Process / GO_Cellular_Component (reused `extract_go_terms()` logic, duplicated rather than imported since `fetch_uniprot.py` runs argparse at module level with no `__main__` guard).

**The ID-matching problem, found and fixed during this run:** a single UniProt entry can map to multiple Ensembl protein IDs (one per isoform — confirmed directly against EGFR, which has 4). Existing CPTAC abundance matrices (`rank_normalized_proteomics.csv`) are already keyed by one specific ENSP ID per protein; if the fresh fetch assigns a *different* isoform ID than what a cohort's file already uses, Stage 2's per-patient abundance lookup would silently report "not detected" for a protein that actually was measured, just filed under a different label. First implementation picked whichever matching ID happened to come first in Python's (unordered) set iteration — verified this was a real bug, not hypothetical: checking the "missing" proteins by gene name (not just exact ID) showed most weren't missing at all, just relabeled to an ID only some cohorts recognized. Fixed by counting, per candidate ID, how many cohorts' abundance matrices actually use it, and deterministically picking the ID with the widest cohort coverage.

**Results (final, after the fix):**
- 20,431 reviewed human UniProt entries fetched
- Dropped: 3,114 with no FUNCTION annotation, 403 with no Ensembl Protein cross-reference at all
- **16,893 total proteins saved** to `data/full_proteome/protein_annotations.csv` (one canonical file — supersedes the union of the 9 cohorts' separate `protein_annotations.csv` files as the identity/text source for Stage 1 going forward; the per-cohort `rank_normalized_proteomics.csv` abundance files are untouched and still used for Stage 2)
- 12,549 matched an ENSP ID already used by a CPTAC cohort; **4,346 are genuinely new** (never detected in any of the 9 cohorts)
- Verified against the old per-cohort data by gene name (not just exact ENSP ID, since IDs can legitimately shift between isoforms): only **9 genes** are genuinely absent versus the old baseline (`C1R, EPHB6, GCKR, INKA1, PLEKHJ1, RAVER1, RPS10-NUDT3, SWI5, ZNF714`) — a small, quantified, accepted data-loss footnote, same pattern as the existing "396 LUAD proteins have no UniProt match" note.

**Citation stripping (found while spot-checking the output):** UniProt FUNCTION comments embed evidence-provenance tags inline, e.g. `"...leading to its degradation (By similarity)."` or `"(PubMed:23056470)"`. These carry no biological content for a text encoder — just noise tokens eating into BioBERT's 512-token budget — and disproportionately affect exactly the well-studied, clinically important proteins the truncation problem in 10n already flagged: proteins with at least one PubMed citation averaged **938 characters** vs. **296** for those without (3.2x longer), confirmed directly on 7,547/16,893 (44.7%) affected proteins. Added `strip_citations()` (regex over `PubMed:\d+`, `By similarity`, `Probable`, `Potential` patterns) to the fetch script and re-ran; 25 residual cases (0.15%, uncommon formatting variants) left uncleaned — negligible, not chased further.

**Noted limitation, logged but deliberately not chased down now (would be new scope):** even after gene-name masking, different proteins — especially paralogs/family members — often still have very similar or near-identical UniProt Function text. This is a softer version of the exact-duplicate problem already solved in 10a (same protein, different cohort, identical text, mathematically-impossible InfoNCE contradiction): here it's *different* proteins with *similar* text, which adds gradient noise rather than a hard contradiction, and existing dedup logic doesn't catch it since dedup only ever targeted the same protein appearing twice. Distinct from query-phrasing effects (8e) — this lives in the training text itself and doesn't go away with more data or different eval queries. Candidate future fix: the paused LLM-fusion approach (10o) produces more differentiated, protein-specific prose, though it draws on the same underlying facts so may not fully resolve it for genuinely near-identical paralogs.

### 11c. CD-HIT clustering and the homology-aware split, over the full proteome
`cluster_proteins_cdhit.py` run at 90% identity (`-n 5`, the CD-HIT-prescribed word length for the 0.7–1.0 identity band) over all 16,890 proteins with both a sequence and an annotation. **Result: 16,400 total clusters** — the overwhelming majority (16,080) are singletons with no near-duplicate at all; only **320 clusters have more than one member** (isoforms / near-identical paralogs), the largest holding 16 sequences. This is the concrete number behind the qualitative claim in 11a: most of the human proteome is *not* redundant at 90% identity, so CD-HIT is doing real, targeted work only for that ~4.8%-of-proteins minority, not reorganizing everything into a handful of big family buckets.

`protein_train_validation_test.py` (rewritten per 11a) shuffled the 16,400 clusters (not individual proteins) with `random.seed(42)` and dealt them into buckets, keeping every cluster intact within one split. **Result, saved to `data/protein_splits_full_proteome.json`:** 1,689 validation / 1,689 test / 13,515 train (of 16,893 usable proteins — the ESM2 ∩ BioBERT intersection).

### 11d. First (unmasked) full-proteome training pass, and what the homology split actually changed
Before generating masked embeddings, ran a first, unmasked training pass as a sanity baseline: `train_protein_level.py --cohorts full_proteome --epochs {500,1000,1500,2000}`, `biobert_embeddings.h5` (unmasked). **Best val_loss was nearly flat across the whole epoch sweep** (500→2000: 3.1648 → 3.1345 → 3.1396 → 3.1136), unlike the clear, monotonic diminishing-returns curve in section 10e's original ablation — a first sign that this dataset's optimization landscape behaves differently from the earlier 9-cohort/non-homology setup, motivating the later hyperparameter sweep (11e) rather than just trusting epoch count as the main lever.

`cross_modal_eval.py` on the e2000 checkpoint, restricted to the new homology-aware 1,689-protein test pool: T→P R@1/5/10/50 = 16.58/37.71/47.42/71.05%, P→T = 16.76/37.48/47.78/70.40%. Compared against the old 9-cohort unmasked baseline on its own (non-homology-split) 1,573-protein pool (33.38/49.33/56.20/72.60% T→P) — **R@1 nearly halved while R@50 barely moved.** Interpretation: this is most plausibly the homology-aware split doing exactly what it was built for (11a) — closing the near-duplicate-paralog leakage that let the old random split's "held-out" proteins often have a near-identical twin still sitting in train. Confounded with the switch to a larger, more diverse protein universe (16,893 vs. 15,733), so not a clean single-variable comparison, but consistent with the leakage-closing story rather than a regression.

### 11e. Masked full-proteome embeddings, and a hyperparameter sweep that found a real confound
Generated `data/full_proteome/biobert_embeddings_masked.h5` (`embed_biobert.py --cohort full_proteome --mask-gene-names`, no GO terms) — the masking decision from 10m folded in as the baseline going forward, not re-litigated as an ablation here given full-proteome training is cheap enough to just always use it.

Before retraining, refactored `train_protein_level.py`: `lr` and `batch_size` became real CLI arguments (`--lr`, `--batch-size`) instead of hardcoded module constants, and every checkpoint now saves `lr`, `batch_size`, `hidden_dim`, `biobert_filename`, and `splits_file` alongside `val_loss`/`epoch`. Motivated by a concrete incident: two manual masked runs (`e500`, `e1000`) produced suspiciously non-monotonic val_loss (2.796 vs. 3.223) and post-hoc inspection showed `BATCH_SIZE` had silently changed between the two runs via a hand-edited module constant, with no record of which run used which value — exactly the ambiguity risk the old constants-based design invited.

**`sweep_lr_epochs.py`** (new script) then ran a full joint grid — `lr ∈ {3e-6, 1e-5, 3e-5, 1e-4}` × `batch_size ∈ {128, 256, 512}` × `epochs ∈ {250, 500, 1000}` = 36 configs, batch size included in the same grid (not sequenced separately) specifically because it was suspected to interact with LR — both plausibly address the same underlying "too few steps per epoch" issue (13,515 train pairs ÷ 512 = only 27 steps/epoch) from different angles.

**Raw val_loss ranking was misleading, and confirmed why:** sorted by raw `best_val_loss`, `batch_size=128` swept the entire top of the table (best: `lr=1e-5, bs=128, e=1000`, val_loss=2.185), with `bs=512` at the bottom (worst: `lr=3e-6, bs=512, e=250`, val_loss=3.824). But InfoNCE's cross-entropy has a batch-size-dependent random-guessing floor of `ln(batch_size)` (a smaller batch is a mechanically easier "which of N is the match" task) — `ln(128)=4.852`, `ln(256)=5.545`, `ln(512)=6.238` — so raw val_loss is not comparable across batch sizes. Correcting with `gap_below_random = ln(batch_size) − val_loss` **completely reversed the ranking**: every one of the corrected top-10 rows is `batch_size=512`, the exact opposite of the raw-val_loss table. This is a real, quantified instance of the same general caution already established elsewhere in this document (val_loss/cross-modal can rank models in the opposite order from the metric that actually matters) — here surfacing *within* a single hyperparameter sweep, not just between checkpoints.

**Shortlist (top 3 by `gap_below_random`), evaluated on pathway AUROC** (the metric the correction can't fix, since it isn't computed from a batch-size-dependent loss at all) — `pathway_auroc_protein_level.py` against the same 245-pathway set used throughout:

| lr | batch_size | epochs | best_epoch | val_loss | overall AUROC (n=245) | test-only AUROC (n=159) |
|---|---|---|---|---|---|---|
| 1e-4 | 512 | 500 | 45 | 3.1808 | **0.6401** | **0.5915** |
| 1e-5 | 512 | 1000 | 469 | 3.1818 | 0.6367 | 0.5885 |
| 1e-4 | 512 | 250 | 47 | 3.1694 | 0.6350 | 0.5874 |

**Winner, agreeing on both AUROC variants: `lr=1e-4, batch_size=512, epochs=500`** (checkpoint `sweep_lr1e-04_bs512_e500_best.pt`) — notably, `batch_size=512` was the *original* CellWhisperer-inherited default the whole sweep set out to question, and it won once fairly compared. For context (not a formal comparison, different protein universe/split): close to the section 10m masked 9-cohort baseline (overall 0.6264, test-only 0.5952) — slightly ahead overall, essentially tied test-only.

### 11f. Projection head dimension search — `hidden_dim` and `output_dim`, and why they can't be tuned independently
With `(lr=1e-4, batch_size=512, epochs=500)` now fixed from 11e, the last architectural question was the projection heads' two dimensions: `hidden_dim` (the MLP's internal layer width, default 512) and `output_dim` (the final shared embedding space where cosine similarity is computed, default 256 — CellWhisperer uses 1024). `train_protein_level.py` gained `--hidden-dim`/`--output-dim` CLI flags (both saved into the checkpoint, same self-documentation pattern as `lr`/`batch_size`); all four evaluation scripts (`pathway_auroc_protein_level.py`, `pathway_recall_at_k_protein_level.py`, `cross_modal_eval.py`, `recall_at_k_protein_level.py`) were updated to read `hidden_dim`/`output_dim` back out of the checkpoint when reconstructing the projection heads, instead of assuming 512/256, so any architecture variant loads correctly.

**A real mathematical constraint, not just an empirical hunch, shaped which combinations were worth testing:** the final layer is `Linear(hidden_dim, output_dim)`, and a linear layer's output can only vary along at most `min(hidden_dim, output_dim)` independent directions (a matrix-rank fact). So `output_dim > hidden_dim` is a structurally invalid test — the embedding would nominally be the larger size but is silently rank-capped at `hidden_dim`, unable to use the extra dimensions for genuinely new information. `hidden_dim ≥ output_dim` (equal or hidden bigger) is always valid. This ruled out testing `hidden=512, output=1024` directly and required raising `hidden_dim` alongside `output_dim` whenever `output_dim` exceeded 512.

**Results, all at the fixed `(lr=1e-4, batch_size=512, epochs=500)`, pathway AUROC on the same 245-pathway set:**

| output_dim | hidden_dim | val_loss | overall AUROC (n=245) | test-only AUROC (n=159) |
|---|---|---|---|---|
| 128 | 512 | 3.3529 | 0.6331 | 0.5780 |
| 256 (original default) | 512 | 3.1808 | 0.6401 | 0.5915 |
| 512 | 512 | 3.1720 | 0.6270 | 0.6052 |
| 256 (hidden-only increase) | 1024 | 3.1951 | 0.6301 | 0.5735 |
| **1024** | **1024** | **3.0669** | **0.6563** | **0.6101** |
| 2048 | 2048 | — | 0.6469 | 0.6001 |

**Disentangling insight:** raising `hidden_dim` alone (1024) while leaving `output_dim` at 256 did **not** help — it scored the worst of every configuration tested, below even the original 512/256 default. This rules out "more MLP capacity" as the explanation for the eventual win. The improvement only appears when both dimensions scale up *together* (1024/1024) — direct evidence that it's the size of the final shared embedding space that matters, and that a wider hidden layer only helps once there's a correspondingly larger output space to make use of it (consistent with the rank-capping argument above).

**2048/2048 confirms 1024 is a genuine peak, not an untested edge:** both AUROC variants drop at 2048 relative to 1024 (0.6469 vs. 0.6563 overall; 0.6001 vs. 0.6101 test-only) — ruling out "bigger is still better, we just stopped too early" and closing this axis of search.

**Final validated architecture, checkpoint `data/runs/full_proteome/final_hparams_masked_best.pt`** (renamed from `outputdim_od1024_best.pt` once confirmed as the winner)**:**
`lr=1e-4`, `batch_size=512`, `epochs=500`, `hidden_dim=1024`, `output_dim=1024` — every one of these five settings individually checked against at least one alternative on pathway AUROC (not val_loss/cross-modal alone), with the batch-size/val_loss confound (11e) and the hidden_dim/output_dim rank-capping confound (11f) both caught and corrected for before drawing conclusions, rather than after.

### 11g. Masking re-verified at the final architecture, and cross-modal vs. pathway AUROC diverge exactly as expected
The masking decision (10m) had been folded into the full-proteome baseline by assumption (11e) rather than re-tested, since the original ablation was run on a different protein universe/split/architecture entirely. To close that gap, trained one more checkpoint — `final_hparams_unmasked_best.pt` — identical to the final architecture (`lr=1e-4, batch_size=512, hidden_dim=1024, output_dim=1024, epochs=500`) in every respect except using `biobert_embeddings.h5` (unmasked) instead of the masked variant, isolating masking as the only variable.

**Cross-modal (`cross_modal_eval.py`), 1,689-protein closed test pool:** mixed, inconclusive — unmasked led on T→P at every K (e.g. R@50: 74.90% vs. 72.23%) while masked led on P→T at R@1/5/10 (e.g. R@1: 22.85% vs. 20.25%), with unmasked again ahead at P→T R@50. No consistent winner either direction.

**Pathway AUROC (the metric that matters) told a completely different, decisive story:**

| | overall AUROC (n=245) | test-only AUROC (n=159) |
|---|---|---|
| unmasked | 0.6373 | 0.5921 |
| **masked** | **0.6563** | **0.6101** |
| **Δ (masking gain)** | **+0.0190** | **+0.0180** |

Masking wins clearly on both AUROC variants. Two things worth noting: (1) this is a clean, single-variable comparison — every other setting is identical — so the gain is directly attributable to masking, not a confound. (2) The overall-AUROC gain (+0.0190) is **almost numerically identical** to the original masking ablation's gain in section 10m (0.6074 → 0.6264, also +0.0190) — the same-sized effect, reproduced on a completely different protein universe, split methodology, and hyperparameter/architecture configuration. This is strong evidence the masking effect is a real, general property of the training text rather than an artifact of one particular setup.

The cross-modal/pathway-AUROC mismatch here is also not a new puzzle — it's the same pattern already documented in section 10p (masking barely moved cross-modal there either), now confirmed a second time on an entirely different architecture: cross-modal is a self-identification task and isn't structurally positioned to detect the benefit of removing a name-based shortcut, since that shortcut barely helps this specific closed-pool task to begin with.

### 11h. Pathway recall@K and self-ID recall@K on the final checkpoint — a clean illustration of the whole name-shortcut narrative
Closing out the eval suite on `final_hparams_masked_best.pt`, two more metrics against the section-10m baseline (`checkpoint_no_abundance_masked_e2000_best.pt`: recall@100/200/400 4.38/7.18/10.97%; self-ID R@1/10/50/100 18.50/36.11/48.70/55.69%).

**Pathway recall@K — real, consistent improvement, in line with the pre-registered prediction:**

| K | old baseline | new final | Δ |
|---|---|---|---|
| 100 | 4.38% | 5.37% | +0.99pp (+23% relative) |
| 200 | 7.18% | 8.27% | +1.09pp (+15% relative) |
| 400 | 10.97% | 12.78% | +1.81pp (+16% relative) |

Test-only variant (positives restricted to never-trained-on test members, n=159 pathways with enough positives): recall@100/200/400 = 2.09%/3.51%/6.26% — naturally lower than the overall numbers (no memorized train/validation positives inflating it), but real, non-zero signal.

**Calibrating "5-13% recall@K" against chance, not against 100%:** the raw percentages look low in isolation, but the right comparison is the random baseline for this pool size, `K / 16,893`: 0.59% at K=100, 1.18% at K=200, 2.37% at K=400. Against that, the model is running at **~9x, ~7x, and ~5x random chance** respectively — a real, non-trivial signal for an open-vocabulary retrieval task (a two-to-four-word category name, no gene names, ranked against ~17,000 candidates) trained on only 13,515 unique examples with a frozen text encoder. It is also, concretely, the best version of this metric across the entire project's history — beating the old 9-cohort baseline (4.38%/7.18%/10.97%) at every K, not a regression. The weakness this number reveals is not a new discovery specific to this checkpoint — it is the same gap section 10l already diagnosed in detail and used to motivate the GO-term/LLM-fusion line of work; this run improves on it without closing it.

**Self-ID recall@K — sharply *worse*, and a second, cleaner demonstration of the homology-split leakage story from 11a/11d:**

| K | old masked baseline (10m) | new final | relative change |
|---|---|---|---|
| 1 | 18.50% | **2.01%** | −89% |
| 10 | 36.11% | 20.31% | −44% |
| 50 | 48.70% | 40.56% | −17% |
| 100 | 55.69% | 50.15% | −10% |

The drop shrinks steadily from R@1 to R@100 — exactly the signature already seen once in 11d's cross-modal comparison (R@1 nearly halved there, R@50 barely moved), now reproduced more starkly on a metric whose candidate pool size barely changed between old and new (~15,718 → 16,893, unlike the cross-modal case which was also confounded by the switch to a bigger protein universe). Interpretation: the old random split let near-identical paralogs of "held-out" proteins sit in the training portion of this same mixed pool, which specifically inflates *exact* top-1 self-identification (a near-twin in training makes rank #1 easy to hit almost by accident) while barely affecting broader top-50/100 concentration. The homology-aware split (11a, 11c) closes exactly this loophole.

**The clean, thesis-relevant story this produces:** as the model improved on every shortcut-resistant metric (pathway AUROC +0.019/+0.018, pathway recall@K +15-23% relative), a shortcut-flavored metric (self-ID recall@K) *fell* sharply — because its old high value was itself partly an artifact of a less rigorous split, not genuine capability. This is the name-shortcut/leakage narrative (first raised in 8a, demonstrated four more ways across 8e/10k/10l/10n) appearing a sixth time, now with the clearest before/after numbers of any of them.

**On cross-modal's realism, worth stating explicitly in the thesis:** cross-modal's closed, unseen-only pool is *not* representative of real deployment — a researcher's real upload would be overwhelmingly proteins the model already trained on (13,515 of 16,893, ~80%) plus a few novel ones, not an all-novel pool. Cross-modal is valuable as a clean generalization stress test and for literature comparability (same protocol as CLIP/Flickr30k benchmarks), not as a predictor of real-world performance. Self-ID recall@K and pathway AUROC/recall@K, which all use the full mixed ~16,893-protein pool, are the metrics that actually approximate a real uploaded sample — and those are the metrics that showed genuine improvement in this final checkpoint.

**Next:** the GO-term augmentation re-ablation on this same full-proteome/homology-split/final-architecture setup (per the decision to get fresh evidence on the final architecture rather than carry over the old 9-cohort GO-term negative result unverified).

**As a bachelor's thesis contribution, independent of the model's absolute performance:** the methodology built this week — objective, pre-registered pathway selection criteria instead of hand-picking (8d), two independently-designed natural-language query experiments reported honestly even where they didn't help (8e), a quantified demonstration of the name-shortcut limitation (R@K vs. AUROC gap), a clearly reasoned architecture plan with an explicit theoretical justification (the abundance-incentive analysis), two independently-discovered evaluation confounds caught and corrected during hyperparameter search rather than after (the batch-size/val_loss random-guessing floor in 11e, and the hidden_dim/output_dim rank-capping constraint in 11f), and a sixth, unusually clean demonstration of the name-shortcut/leakage narrative — self-ID recall@K falling sharply while every shortcut-resistant metric improved on the same final checkpoint (11h) — is itself a legitimate, rigorous scientific contribution. A thesis that honestly reports what works, what doesn't, and why is stronger than one that oversells a higher raw metric. Whether the patient-specificity claim becomes genuinely solid depends on the retraining plan and `activity_score` validation still ahead — an open question, not a settled one, and it should be presented that way in the thesis.

### 11i. Split-control diagnostic: confirming the homology-split effect is real, not a hyperparameter-change artifact
Section 11h's comparison (old 9-cohort/random-split checkpoint vs. new full-proteome/homology-split/final-architecture checkpoint) changed three things at once — protein universe size, split method, *and* hyperparameters/architecture (the 11e/11f sweep) — so the self-ID recall@K crash and pathway-metric gains couldn't be cleanly attributed to the split change alone. Added `--random-control` to `protein_train_validation_test.py`: shuffles individual proteins instead of CD-HIT clusters, over the identical full-proteome protein set, written to `data/protein_splits_full_proteome_random.json` rather than overwriting the real split. Trained `split_control_random` (final hyperparameters, random split) and `split_control_old_hparams` (old pre-sweep hyperparameters, homology split) to isolate each variable.

**Result (245-pathway set):**

| Config | overall AUROC | test-only AUROC |
|---|---|---|
| old hparams + homology split | 0.638 | 0.589 |
| final hparams + **random** split | 0.645 | 0.592 |
| final hparams + **homology** split (real checkpoint, 11f) | 0.656 | 0.610 |

Both changes contribute independently and positively: hyperparameter tuning adds ~+0.018 (0.638→0.656 at fixed homology split), and the homology split adds ~+0.012–0.018 on top of that (0.645→0.656 at fixed final hyperparameters). The homology-aware split isn't just a stricter/lower-scoring fairness correction — it genuinely scores *better* than random per-protein splitting even at matched hyperparameters, not merely more honest. Nothing was double-counted between the two changes.

### 11j. Discovered test-set leakage in the 11e/11f hyperparameter/architecture selection — added `validation_only_auroc`
Re-examining exactly how the 11e/11f winners were chosen surfaced a real methodological gap, not just a style preference. The 36-config lr/batch_size/epochs grid was correctly narrowed to a shortlist of 3 using `val_loss` (corrected for the batch-size-dependent `ln(batch_size)` floor) — that part only touched the **validation** split, cleanly. But the *final* pick among those 3, and the entire `hidden_dim`/`output_dim` search (11f, 6 configurations), were decided by comparing `test_only_auroc` across multiple candidates and choosing the winner — i.e., the **test** split was used for model selection, not just for a single final report. Milder than a full search directly optimizing test AUROC (a handful of candidates compared, not dozens), but the same category of mistake: the reported test-only AUROC for the final checkpoint (0.6101) is likely mildly optimistic, since the winning configuration was partly chosen *because* it scored well on those same 245 test pathways.

**Fix:** `pathway_auroc_protein_level.py` now computes a third number per pathway, `validation_only_auroc` — identical logic to `test_only_auroc`, but restricted to validation-split proteins as positives instead of test-split proteins. This is now the metric for all future hyperparameter/checkpoint/architecture comparisons; `test_only_auroc` is reserved for a single, final, untouched check on whichever configuration wins, never used to pick between candidates again. (Precedent for why this distinction matters in practice, not just in principle: the original CLIP paper tuned hyperparameters cheaply on an in-distribution proxy — grid/random/manual search on a 1-epoch baseline ResNet-50 — and never touched its ~30 zero-shot transfer benchmarks during tuning, only for the final reported result.)

### 11k. Clean, two-stage W&B hyperparameter re-tuning (in progress, not yet run)
Decision: redo the lr/batch_size/epochs search (superseding 11e) and the hidden_dim/output_dim search (superseding 11f) properly, using `validation_only_auroc`, orchestrated through Weights & Biases rather than a hand-rolled grid script — partly for the methodological fix above, partly because a W&B sweep dashboard is a more presentable thesis artifact than a hand-parsed CSV, and partly for hands-on tool experience.

**Design, staged rather than one joint search** (standard "tune one group, hold the rest fixed, then refine" strategy — not a shortcut):
- **Stage A (built, not yet run):** Bayesian search over `lr` (continuous log-uniform, 1e-6 to 1e-3) × `batch_size` (categorical, 128/256/512) × `epochs` (categorical, 500/1000/2000 — included rather than fixed-high-with-best-checkpoint-tracking, because the total epoch budget changes the *shape* of the cosine LR-decay schedule itself, not just training duration, per 11e's own schedule-phase finding). `hidden_dim`/`output_dim` held fixed at **512/512** — ProteinCLIP's stated shared embedding dimension, a citable starting point (though ProteinCLIP's protein encoder is the larger ESM2 650M/1280-dim, vs. this project's deliberately smaller ESM2 150M/640-dim — matches their output-space choice only, not the full architecture). Optimizes `final_validation_only_auroc`.
- **Stage B (planned):** search over `hidden_dim`/`output_dim` (same candidate set as 11f, respecting `output_dim ≤ hidden_dim`), with Stage A's winning `lr`/`batch_size`/`epochs` locked in, also scored on `validation_only_auroc`.
- **Final step (planned), exactly once:** `test_only_auroc` computed on the fully-locked-in winning configuration from both stages — the one honest number reported in the thesis.

Sweep definition: `sweep_config_stage_a.yaml`.

### 11l. v1 hyperparameter sweep — simple, val_loss-based, deliberately decoupled from AUROC evaluation (2026-07-24)
`wandb login` is now done, but rather than running Stage A (11k) first, a simpler, parallel "v1" sweep was built and prioritized: a joint Bayesian search over `lr`/`batch_size`/`epochs`, selected purely via the **validation split's InfoNCE loss** — never touching pathway AUROC or the test split at all. Deliberate scoping decision: hyperparameter tuning is a supporting step for this thesis, not the primary contribution (evaluation methodology and training-data quality are, per 10p/11h) — so tuning and evaluation are kept structurally decoupled, avoiding any risk of repeating the 11j leakage pattern (test-set metric used for repeated model selection). New files: `sweep_config_v1_lr_only.yaml`, `src/model/sweep_train_lr_only.py` (separate from Stage A's `sweep_config_stage_a.yaml`/`sweep_train.py` — both sweep infrastructures now coexist, Stage A still unrun).

**Search space:**
- `lr`: log-uniform, 1e-5–1e-3 — brackets CellWhisperer's 1e-5 and ProteinCLIP's 1e-4 (see below)
- `batch_size`: {128, 256, 512} — stays safely above CellWhisperer's own finding that batch_size=32 (16x smaller than their 512 default) significantly degrades performance
- `epochs`: {100, 200, 400} — lower bound *derived*, not guessed: at the smallest swept `batch_size` (512, ~26 steps/epoch on this dataset), `epochs=100` gives ~2,600 total steps, clearing `train_protein_level.py`'s own `MIN_RECOMMENDED_STEPS=2000` sanity threshold; `epochs=50` would fall to ~1,300 steps, below it. Upper bound (400) follows conventional geometric spacing, not a separately derived constraint.
- Fixed: `hidden_dim=512`, `output_dim=128` (see correction below), `temperature=0.07` (hardcoded in `infonce_loss`, matches original CLIP), `early_stopping_patience=10` (added as an opt-in parameter to `train_protein_level.py`'s `train()`, default `None` preserves old behavior for all other callers).

**Selection metric — `gap_below_random`, not raw `val_loss`:**
```
gap_below_random = ln(batch_size) − val_loss
```
InfoNCE's random-guessing floor for a batch of size N is exactly `ln(N)` (the expected cross-entropy of a model with zero learned signal) — this floor differs per swept `batch_size` candidate, so raw `val_loss` would systematically favor smaller batches regardless of true model quality. Maximized, tracked via `wandb.define_metric("gap_below_random", summary="max")` so early stopping doesn't distort a run's reported best value. This is the same correction already validated once in this project's earlier grid search (11e) — applied here proactively from the start, not discovered after the fact.

**Architecture citation error found and corrected via primary-source verification:** the existing assumption (already present in 11f/11k as "ProteinCLIP's stated shared embedding dimension, 512, a citable starting point") was **wrong**. Direct verification against the actual ProteinCLIP paper text confirmed `dshared = 128`, explicitly chosen to be "significantly smaller than all language models used in this study" (their inputs up to 1280-dim). `output_dim` corrected 512 → 128 for this v1 sweep accordingly. Note this same incorrect citation is still present in Stage A's fixed values (11k, line above) — Stage A remains unrun, so this should be revisited before Stage A is ever launched. ProteinCLIP's projection-head design otherwise matches this project's existing architecture (single hidden layer, chosen in their own paper via an explicit 0/1/2/3-hidden-layer validation-set ablation — 2-3 layers overfit, 1 layer balances expressiveness against overfitting risk) — this project's `hidden_dim=512` (not tied per-head to each input's own dimension, unlike ProteinCLIP's `d→d→dshared` design) and fixed (not learned) `temperature=0.07` are documented as deliberate simplifications, not silent deviations.

**Search range validated against ProteinCLIP's actual training budget:** ProteinCLIP's paper reports 465,770 sequence-annotation pairs (14,514 organisms), `batch_size=20,480`, `lr=1e-4`, `epochs=300`, AdamW. Directly copying these absolute values is infeasible — `batch_size=20,480` alone exceeds this project's entire deduped training set (13,515 pairs) by ~1.5x, the same category of scale mismatch as raw CLIP's `batch_size=32,768` (though far less extreme: CLIP's dataset is ~30,000x larger than this project's, ProteinCLIP's is only ~34x larger). Converting to total optimizer steps — the only unit comparable across such different dataset sizes, per the same reasoning already applied to CellWhisperer:
```
465,770 ÷ 20,480 ≈ 23 steps/epoch
23 × 300 ≈ 6,820 total steps
```
This falls **inside** this project's own independently-derived search range (2,640–42,240 total steps across the full `batch_size`×`epochs` grid) — a numeric validation that the search range is well-calibrated against the most directly comparable prior work (same frozen-encoder, small-projection-head architecture family), despite being derived from this project's own much smaller dataset rather than copied from ProteinCLIP's numbers. `lr=1e-4` also falls inside the searched range and matches this project's own earlier (11e) empirically-found best value. As a secondary sanity check: ProteinCLIP's batch size is ~4.4% of their dataset per step (20,480/465,770); this project's swept batch sizes are ~0.9–3.8% of its own dataset (128–512/13,515) — a similar proportion, though not something deliberately targeted.

**Citation caveat:** the paper is referred to here as "ProteinCLIP" (bioRxiv, DOI 10.1101/2024.05.14.594226, "ProteinCLIP: enhancing protein language models with natural language") — the exact author list was not independently verified in this session and should be confirmed directly from the paper before citing in the final thesis text. A separate paper, ProtET ("Multi-Modal CLIP-Informed Protein Editing," already referenced in 11a), was initially and incorrectly conflated with ProteinCLIP mid-session (both are protein-text CLIP-style works with similar names and overlapping hyperparameter ranges: ProtET reports `batch_size=128`, `epochs=10`, `lr=5e-5`, `2,000 linear warmup steps`, ESM2-650M + PubMedBERT, `dshared=512`, `temperature=0.01`) — resolved by reading the actual paper text directly rather than trusting an earlier automated web-search summary, which itself also turned out to be imprecise. Lesson: for numbers that matter enough to justify a thesis design choice, verify against primary-source text, not search-tool summaries.

**Status:** sweep infrastructure built, verified, and launched by the user (`uv run wandb sweep sweep_config_v1_lr_only.yaml`, `wandb agent ... --count 30`). This is the tuning approach actually used for the model going forward. Stage A/B (11k)'s files (`sweep_config_stage_a.yaml`, `src/model/sweep_train.py`) were subsequently deleted (not just deprioritized) once this v1 approach was decided on — `pathway_auroc_protein_level.py`'s `validation_only_auroc` addition (11j) is kept regardless, since it is a general-purpose evaluation capability independent of Stage A's now-removed sweep script.

### 11m. DeepLoc zero-shot subcellular-localization classification (2026-07-25)
A new evaluation type, deliberately different in kind from pathway AUROC (11g/11h): pathway AUROC is a ranking metric computed one pathway at a time, while this is a small, fixed, mutually-exclusive forced-choice classification task — closer to conventional zero-shot image-classification benchmarks (CLIP-style), and a sanity check that doesn't depend on gseapy/KEGG at all.

**Data (`src/evaluation/build_deeploc_eval_set.py` → `data/evaluation/deeploc_human_test_set.csv`):** DeepLoc-1.0 (Almagro Armenteros et al. 2017) is a general eukaryote dataset (~14,000 proteins across many species), not human-specific — using it as-is would let non-human proteins into an eval meant to test a model trained entirely on human CPTAC data. Filtered to human-only by intersecting DeepLoc's UniProt accessions with our own already-vetted `data/full_proteome/protein_annotations.csv` (organism_id:9606, reviewed-only) rather than a fresh taxonomy lookup — any accession that made it into our own human-only pull is human by construction, at the small, accepted cost of missing a handful of proteins whose accession has been merged/updated since DeepLoc's 2017 publication. Also dropped 146 dual-localization entries (e.g. "Cytoplasm-Nucleus") since this is single-label argmax classification, not multi-label. Result: **2,645 human proteins** across DeepLoc's 10 classes. Seen/unseen is assigned relative to *our own* model's protein-level train split (`data/protein_splits_full_proteome.json`) — seen = protein was in training (2,134), unseen = held out in validation/test (511) — not DeepLoc's own original train/test partition (kept only as an uninspected informational column), which is irrelevant here since this is zero-shot: no training on DeepLoc labels happens at all.

**Method (`src/evaluation/zero_shot_deeploc_eval.py`):** standard CLIP zero-shot classification (Radford et al. 2021, sec. 3.1.4) with prompt ensembling — each of the 10 classes gets 3 independently-phrased natural-language templates (e.g. *"A protein located in the nucleus."*, *"This protein is found in the nucleus and carries out its function there."*, *"Subcellular localization: the nucleus."*), each encoded and L2-normalized, averaged, then re-normalized into one class embedding (re-normalizing after averaging matters: skipping it would let classes whose 3 templates happen to agree more end up with larger-norm embeddings, silently biasing the argmax toward them). Test proteins are embedded via the existing protein tower; predicted class = argmax cosine similarity against the 10 class embeddings. Accuracy, macro-F1, and a confusion matrix (fixed label order) are computed separately for seen/unseen/all, plus the generalization gap and two baselines (random = 1/n_classes; majority-class = data-dependent per subset). Results are checkpoint-suffixed CSV/JSON so future checkpoints can be logged and compared without clobbering prior runs — same convention as `pathway_auroc_protein_level.py`.

**Results** (checkpoint `final_v2_dims_masked_best.pt`, `hidden_dim=2048`, `output_dim=1024` — read directly from the checkpoint's own saved metadata; this checkpoint is from a hyperparameter/architecture sweep continuation beyond what 11l documents, provenance not yet written up in this file, flagged here rather than left implicit):

|---|---|---|---|---|---|

| 10-way | seen | 18.09% | 0.168 | 10.00% | 37.07% |
| 10-way | unseen | 16.24% | 0.146 | 10.00% | 35.62% |

**Findings:**
1. **The model underperforms the majority-class baseline in every variant tested** (best: 19.6% vs. 36.8% for "always guess Nucleus"). Zero-shot subcellular-localization classification is a genuine weak point for this checkpoint, not an artifact of the eval construction.
2. **Dropping the structurally-impossible "Chloroplast" class (0 human members, so every prediction of it is a guaranteed miss) helped only marginally** (+1.7pp) — most of the gap survives its removal, so it wasn't the primary driver.
3. **Class-wise mean-centering calibration — tested as a cheap, no-retrain fix, failed to help** (±0.2pp, actually slightly worse on unseen). Diagnosed via the raw prediction distribution before calibration: Nucleus (37% of true labels, the largest class) was predicted only ~5% of the time, while Lysosome/Vacuole and Peroxisome (together <2% of true labels) were over-predicted 10–13x. The natural hypothesis — some class prompts sit at a constant, generically-higher cosine similarity regardless of the protein — did not hold up: per-class mean similarities turned out nearly identical (span of only ~0.03), and the most over-predicted class (Peroxisome) did not even have an above-average mean. This rules out a simple additive per-class bias as the mechanism. The more likely explanation — per-class *variance* rather than mean (a class with more spread-out similarity scores wins argmax disproportionately often on its high tail even with an unremarkable average) — was identified but not tested further; would require z-score standardization instead of centering. Deliberately left as a stopping point rather than pursued further in this session.
4. **The seen/unseen generalization gap stays small throughout (~1–2pp) across all three variants** — a consistent, real limitation across both trained and never-trained proteins, not a memorization artifact (contrast with the self-ID recall@K leakage story in 11h, where old-split vs. new-split numbers differed sharply).
5. **Plausible, untested root cause:** Stage 1's training text is UniProt FUNCTION annotation, not dedicated location text — subcellular localization is likely only incidentally present in that text, unlike pathway/function concepts where this model family scores considerably better (pathway AUROC overall ~0.60+, see 11f/11h). Noted as a hypothesis for future investigation, not yet directly tested.

**Status:** both `build_deeploc_eval_set.py` and `zero_shot_deeploc_eval.py` are done and reusable — rerun the eval script against any future checkpoint (`--checkpoint`, `--biobert-filename`, optional `--drop-chloroplast`/`--calibrate`) to log and compare. The z-score-standardization follow-up to finding 3 is the natural next step if this gets revisited.
