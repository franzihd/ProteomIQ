# ProteomIQ

A protein-level joint embedding space for proteomics and natural language, trained contrastively on CPTAC, that allows a researcher to query the biological meaning of proteins in their own patient sample using natural language.

## Project goal

Build a CLIP-style model at **protein granularity**:
- Each training pair is one `(protein, patient)` combination — the protein's amino acid sequence embedding (from ESM2) combined with its measured abundance value in that patient
- The matching text description combines the protein's UniProt functional annotation with the clinical context of that patient
- At inference: a researcher provides a text query (e.g. "proteins associated with lung cancer") and a new patient sample; nearest-neighbor search over that sample's ~8,000 protein embeddings returns the most biologically relevant proteins

**Why protein-level (not patient-level):** querying at the patient level returns other patients — not useful. Querying at the protein level returns specific proteins like EGFR, MET, KRAS — directly actionable biological insight.

The closest prior work is [CellWhisperer](https://github.com/theislab/CellWhisperer), which does the same for single-cell transcriptomics (scRNA-seq). ProteomIQ targets mass-spectrometry-based proteomics instead.

## Architecture

### Training
```
protein sequence → ESM2 (frozen, pre-computed) ─┐
                                                  ├─→ MLP projection → embedding
abundance scalar (from CPTAC) ────────────────────┘

UniProt description + patient clinical text → BioBERT → MLP projection → embedding
```
Contrastive loss (NT-Xent / InfoNCE) pulls matching `(protein_in_patient, text)` pairs together and pushes non-matching pairs apart.

Scale: ~1,100 patients × ~12,000 proteins ≈ **13 million training pairs** across all CPTAC cohorts. Initial development uses LUAD only (~1.7M pairs).

### Inference
```
researcher query text → BioBERT → embedding
                                       ↓
                    nearest-neighbor search over ~8,000 protein vectors
                    (pre-encoded from the new patient sample)
                                       ↓
                    ranked list: EGFR (0.94), MET (0.91), KRAS (0.87) …
```

### Key design decisions
- **ESM2 is frozen** — run once on all protein sequences offline, embeddings saved to disk. Only the MLP projection heads are trained. This makes training feasible without fine-tuning a large model.
- **ESM2 model choice**: `esm2_t30_150M` (150M params) is the recommended balance of quality vs. compute. `esm2_t6_8M` is faster for prototyping.
- **Abundance as scalar**: concatenated to the ESM2 embedding before the MLP. Encodes expression level as a biological signal.
- **Text = UniProt + clinical**: UniProt annotation is static per protein (reused across all patients); clinical description is static per patient (generated by `text_generation.py`). Concatenated to form the per-`(protein, patient)` text.

## Domain glossary

- **Proteomics**: large-scale study of all proteins expressed in a cell, tissue, or organism — measured with mass spectrometry
- **CPTAC**: Clinical Proteomic Tumor Analysis Consortium — the main data source (`cptac` Python package)
- **LUAD**: Lung Adenocarcinoma — the cancer type currently used as the first dataset
- **Protein abundance matrix**: rows = samples (patients), columns = proteins (identified by gene name + database ID, stored as a two-level MultiIndex), values = measured expression levels
- **NaN**: Not a Number — missing value, common in proteomics when a protein was not detected in a sample
- **CLIP**: Contrastive Language-Image Pretraining — trains two encoders (one per modality) with a contrastive loss so matching pairs end up close in a shared embedding space
- **Contrastive loss**: loss function that pulls embeddings of matching pairs together and pushes non-matching pairs apart; NT-Xent and InfoNCE are common variants
- **Nearest-neighbor search**: given a query embedding, find the k most similar embeddings by cosine or Euclidean distance (e.g. via FAISS or `sklearn`)
- **ESM2**: protein language model by Meta, pre-trained on millions of protein sequences; produces rich per-protein embeddings that capture structure and function. Used here as a frozen feature extractor.
- **UniProt**: protein database containing curated functional annotations for human proteins (gene function, biological process, disease associations); the source of protein-side text descriptions
- **NT-Xent / InfoNCE**: the standard contrastive loss used in CLIP — for each sample in a batch, the matching pair is the positive and all other pairs are negatives

## UniProt fetching

`src/Textual/fetch_uniprot.py` fetches protein annotations and sequences for all proteins in the LUAD proteomics data.

**How it works:**
1. Extracts ENSP IDs from the second header row of `proteomics_raw.csv`
2. Submits a batch ID mapping job to the UniProt REST API (`Ensembl_Protein` → `UniProtKB`)
3. Polls the status endpoint until the job is done
4. Paginates through all result pages (25 per page) following `Link` headers
5. Saves to `data/luad/protein_annotations.csv`

**Output columns:** `ENSP_ID`, `UniProt_Accession`, `Gene`, `Annotation`, `Sequence`

**API note:** UniProt caches job submissions — same input always returns the same `jobId`. The stream endpoint (`/idmapping/stream/`) can expire; use the status endpoint with pagination instead.

**Annotation format:** gene name is prepended to the annotation text, e.g. `"ARF5: GTP-binding protein involved in protein trafficking..."` so BioBERT always sees the protein name.

## Text generation

The text side of each training pair is: **UniProt protein description** + **patient clinical description**, concatenated at training time (not saved to disk — would be ~1.27M rows).

**Do not save combined texts to disk.** Generate `(protein, patient)` pairs on-the-fly during training by joining `protein_annotations.csv` and `descriptions.csv`. Only save the resulting BioBERT embeddings (1.27M × 768 floats ≈ ~4GB).

`src/text_generation.py` handles the patient clinical description half. It converts a clinical metadata row into a natural-language sentence for BioBERT embedding. Each description is a flexible comma-separated sentence — only fields with valid values are included, so length varies per patient.

`src/text_generation.py` handles the patient clinical description half. It converts a clinical metadata row into a natural-language sentence for BioBERT embedding. Each description is a flexible comma-separated sentence — only fields with valid values are included, so length varies per patient.

The UniProt description half (one per protein, reused across patients) is not yet implemented.

**Public API:**
- `is_usable(value)` — returns `False` for NaN, any value in `SKIP_VALUES`, or strings starting with `"Other:"`; `True` otherwise
- `clinical_to_text(row, cancer_type)` — builds a description string from one patient row; `cancer_type` is passed as a parameter (e.g. `"lung adenocarcinoma"`)
- `generate_descriptions(clinical_df, cancer_type)` — applies `clinical_to_text` to every row; returns `{patient_id: description}` dict
- `save_descriptions(descriptions, output_path)` — writes the dict as a CSV with patient ID as index and a `"description"` column

**Columns used** (in order):
- `age`, `sex` — patient demographics
- `ethnicity_race_ancestry_identified` — ancestry
- `tumor_stage_pathological` — Stage I/II/III/IV
- `histologic_type` — adenocarcinoma subtype
- `histologic_grade` — G1/G2/G3
- `tumor_size_cm` — tumor size in cm
- `tumor_laterality` — left or right lung
- `tumor_site` — upper/lower/middle lobe
- `tumor_focality` — unifocal or multifocal
- `tobacco_smoking_history` — mapped to: "lifelong non-smoker", "current smoker", "former smoker (>15 years)", "former smoker (<15 years)"
- `alcohol_consumption` — mapped to: "lifelong non-drinker", "moderate drinker", "heavy drinker", "former drinker"
- `bmi` — categorized as "underweight" (<18.5), "normal weight" (<25), "overweight" (<30), "obese" (≥30), shown with raw value

**Key design decisions:**
- Values in `SKIP_VALUES` (a long list covering "Unknown", "Not Reported", "not specified", etc.) are silently omitted
- Raw verbose smoking/alcohol strings are mapped to short phrases via lookup dicts (`SMOKING_DICT`, `ALCOHOL_MAP`); unrecognized values fall through as-is
- `cancer_type` is passed as a parameter, not read from the CSV
- BioBERT handles variable-length sentences — no fixed template needed

## BioBERT embedding

`src/BioBERT/embed_biobert.py` pre-computes all BioBERT text embeddings for LUAD and saves them to `data/luad/biobert_embeddings.h5`.

**What it computes:** for every `(protein, patient)` pair, it concatenates the protein's UniProt annotation + the patient's clinical description into one string and runs it through BioBERT. Result: one 768-dim embedding per pair.

**Output file structure (`biobert_embeddings.h5`):**
- `embeddings` — shape `(111, 11485, 768)`, float32 — the main cube. `embeddings[p, q, :]` = embedding for patient `p`, protein `q`
- `patient_ids` — array of 111 patient ID strings (row index)
- `protein_ids` — array of 11485 ENSP ID strings (column index)
- `completed` — boolean array of length 111. `completed[p] = True` means patient `p` is fully written to disk

**Resume logic:** the script supports stop/resume. On first run it creates the file (`"w"` mode). On restart it opens the existing file (`"r+"` mode), reads `completed`, and skips any patient already marked `True`. After writing each patient's embeddings, it immediately sets `completed[p_idx] = True` on disk — so stopping mid-run loses at most one patient's work.

**To restart from scratch:** `rm data/luad/biobert_embeddings.h5` then rerun.

**Runtime:** ~60 minutes on RTX A6000 for all 111 LUAD patients.

**To run:**
```bash
uv run python src/BioBERT/embed_biobert.py
```

## GPU / CUDA setup (de.NBI server)

**Hardware:** NVIDIA RTX A6000 (46 GB VRAM), CUDA driver 12.2 (version 535.288.01)

**PyTorch version:** `torch==2.6.0+cu118` — installed from `https://download.pytorch.org/whl/cu118`.
- cu118 = compiled for CUDA toolkit 11.8, fully compatible with driver 12.2 (backward compatible)
- cu121 was tried first but torch 2.6.0 is not available for cu121
- torch 2.5.1 was tried but `transformers>=5.x` requires torch>=2.6 due to CVE-2025-32434

**Why CUDA libraries need LD_LIBRARY_PATH:**
PyTorch depends on several CUDA libraries (cuDNN, NCCL, cuRAND, etc.). These are installed as Python packages (e.g. `nvidia-cudnn-cu12`) but their `.so` files end up inside the venv at non-standard paths like `.venv/lib/python3.11/site-packages/nvidia/cudnn/lib/`. Linux's dynamic linker doesn't know to look there, so PyTorch crashes at import. The fix is to add all these paths to `LD_LIBRARY_PATH`.

**Required export (add to `~/.bashrc` to make permanent):**
```bash
export LD_LIBRARY_PATH=/home/franziska/bachelor/ProteomIQ/.venv/lib/python3.11/site-packages/nvidia/cublas/lib:/home/franziska/bachelor/ProteomIQ/.venv/lib/python3.11/site-packages/nvidia/cuda_cupti/lib:/home/franziska/bachelor/ProteomIQ/.venv/lib/python3.11/site-packages/nvidia/cuda_nvrtc/lib:/home/franziska/bachelor/ProteomIQ/.venv/lib/python3.11/site-packages/nvidia/cuda_runtime/lib:/home/franziska/bachelor/ProteomIQ/.venv/lib/python3.11/site-packages/nvidia/cudnn/lib:/home/franziska/bachelor/ProteomIQ/.venv/lib/python3.11/site-packages/nvidia/cufft/lib:/home/franziska/bachelor/ProteomIQ/.venv/lib/python3.11/site-packages/nvidia/cusparse/lib:/home/franziska/bachelor/ProteomIQ/.venv/lib/python3.11/site-packages/nvidia/nvjitlink/lib:/home/franziska/bachelor/ProteomIQ/.venv/lib/python3.11/site-packages/nvidia/nccl/lib:/home/franziska/bachelor/ProteomIQ/.venv/lib/python3.11/site-packages/nvidia/curand/lib:$LD_LIBRARY_PATH
```

**If `torch.cuda.is_available()` returns False after a fresh terminal:** the LD_LIBRARY_PATH export is missing. Either re-run the export above or check that it is in `~/.bashrc`.

**If uv sync breaks CUDA:** uv sometimes reverts nvidia packages. Run `uv sync --reinstall-package nvidia-nccl-cu12` if NCCL goes missing.
